# AsyncAPI for the job queue and NOTIFY wires

Recommendation, moderate confidence: adopt it for the job queues as a second
document, `apps/api/asyncapi.queues.yaml`, beside the WebSocket document
`apps/api/asyncapi.websocket.yaml`, both generated through
`scripts/generate-asyncapi-module.mjs`. No official AsyncAPI tool emits zod or
runtime guards, so the parser-plus-`json-schema-to-zod` pipeline from the
[live-protocol study](./2026-10-16-push-transport-and-asyncapi.md#d6-contracts-asyncapi-document-first-records-from-openapi)
remains the generator; it gains a per-channel output mode. The NOTIFY payload
is a candidate for the same treatment with a weaker case than first assumed
(F5).

## Wires in scope

| Wire                               | Producer                          | Consumer            | Payload                                                        | Guard before the queue document                               |
| ---------------------------------- | --------------------------------- | ------------------- | -------------------------------------------------------------- | ------------------------------------------------------------- |
| `runs`                             | `RunDispatchService`              | `RunsWorkerService` | `RunJob`; `userMessage.parts` is the stored message-part array | hand `parse` in `src/runs/run-queues.ts`                      |
| `search-reindex`, `search-embed`   | search dispatch                   | search workers      | `{ chatId, ownerUserId }`                                      | hand `parse` in `src/search/reindex-queues.ts`                |
| `search-sweep`, `sessions.cleanup` | pg-boss cron                      | workers             | empty marker                                                   | none needed                                                   |
| `<name>.dead`                      | pg-boss on retry exhaustion       | none in code        | same as source queue                                           | inherits source `parse`                                       |
| `llame_changes` NOTIFY             | SQL trigger `llame_notify_change` | `ChangeHub`         | `ChangeNotification` union keyed by `k`                        | hand `parseChangeNotification` in `src/live/live-messages.ts` |

The pg-boss envelope (`id`, `singletonKey`, retry state) is engine metadata and
stays out of the payload schema.

## Findings

### F1 The spec fits one application that both sends and receives

AsyncAPI "does not assume any kind of software topology", an application
"MUST be a sender, a receiver, or both", and a document "SHOULD describe the
operations an application performs"[^spec-310]. The API process and its
co-located or dedicated workers are one application built from one codebase,
so one document carrying a `send` operation (enqueue) and a `receive`
operation (consume) per channel is the spec's own model. The spec's warning
against deriving a receiver document from a sender document[^spec-310]
concerns two applications and does not apply. A cron queue's `send` is
performed by pg-boss's scheduler; the operation's summary says so.

### F2 No binding exists; `protocol` and `x-` extensions carry the rest

The bindings repository has 18 bindings, none for Postgres, pg-boss, or a
database-backed queue[^bindings]. `server.protocol` is a free string
("The protocol this server supports for connection"), and every object accepts
`^x-` specification extensions, which "may or may not be supported by the
available tooling"[^spec-310]. A document with `protocol: postgres` and a
channel-level `x-llame-queue: { policy: stately, retryLimit: 5, retryBackoff: true }`
parses with `@asyncapi/parser` 3.6.3, the version the repository pins, with
zero diagnostics.

Declaring `protocol: sqs` to borrow its binding would misdescribe the
transport. The SQS binding is the closest standard vocabulary: it models the
dead-letter queue as its own queue, links it through
`redrivePolicy.deadLetterQueue` plus `maxReceiveCount`, and names the lock
window `visibilityTimeout`[^sqs-binding], which correspond to pg-boss
`deadLetter`, `retryLimit`, and the heartbeat window. `x-llame-queue` keeps
pg-boss's own option names instead, because they are what `QueueOptions`
passes to the engine.

A `$ref` from one multi-format schema to another fails the parser
(`Property "schemaFormat" is not expected to be here`). The WebSocket
document needs the OpenAPI format only to reference `openapi.json`; the queue
document references nothing there and uses the default schema format.

### F3 No official tool generates runtime validators

- The Generator renders templates and directs model generation to
  Modelina[^generator].
- Modelina's TypeScript output is classes or interfaces with optional JSON
  marshalling; it has no zod or runtime-validation preset[^modelina-ts].
  Types alone duplicate what `defineQueue<T>` already gives at compile time.
- The official validation guide names `asyncapi-validator`[^message-validation],
  which validates through AJV at runtime[^asyncapi-validator]. Its registry
  metadata was last modified on 2025-03-10, it validates by message key rather
  than producing typed values, and it would add a second validation engine
  beside zod.
- Zod 4's `z.fromJSONSchema()` converts at runtime and is documented as
  experimental[^zod-json-schema]; it yields no static types.

The in-repo generator uses the official parser for validation and
`json-schema-to-zod` for emission. Its live mode requires exactly one `send`
operation and emits a single discriminated union; the `--channels` mode emits
one `<channel>Channel` constant per channel carrying the address, the
`x-llame-queue` options, and the payload schema.

### F4 Payloads persist across deploys, so compatibility matters more than on the socket

A queued, retrying, or dead-lettered job may be read by a different deploy than
the one that wrote it; `src/queue/queue.ts` states this as the reason for
`parse`. Two consequences:

- `@asyncapi/diff` 0.5.0 does not detect payload breaks. It runs on 3.1
  documents, but adding a required field to a payload is reported as
  `unclassified` on every path, with nothing under `breaking`
  ([probe output](./2026-10-17-queue-wire-asyncapi-diff-probe.json)). The
  CLI wrapper `asyncapi diff`[^cli-usage] requires Node 24 in `@asyncapi/cli`
  6.2.0, above the repository's Node 22 pin. A compatibility gate would have
  to be llame's own rule over the payload schemas.
- Generated guards must not tighten acceptance by accident. The hand guards
  ignored unknown fields and checked `parts` only as an array of objects.
  Leaving `additionalProperties` unset makes the generated zod objects strip
  unknown keys, which keeps that acceptance, so a job written by a newer
  deploy survives a rollback. `z.number().int()` in zod 4 enforces the safe
  integer range the hand guard checked for `seq`.

### F5 The NOTIFY payload is covered end to end only in part

`llame_notify_change` builds JSON in PL/pgSQL and TypeScript parses it with a
hand guard, so no shared type crosses that boundary. The gateway integration
test drives a chat rename and a Run through the database and asserts the
socket messages, so a trigger-side rename of the `chat` or `run` fields fails
CI. The `project`, `pin` and `run_event` variants are exercised only by unit
tests over hand-built payloads. Describing `llame_changes` as a channel with a
`oneOf` discriminated on `k` would make the contract declarative and cover
every variant uniformly; the defect it prevents is narrower than for the
queues.

### F6 The counterargument

The WebSocket document paid for itself because a second workspace (`apps/web`)
consumes the wire and records needed provable agreement with `openapi.json`.
The queues have one producer and one consumer in one TypeScript workspace that
already shared `RunJob` by import, behind roughly 70 lines of hand guards.
What AsyncAPI adds is narrower: guards that cannot drift from the documented
shape, queue names and static options taken from the same document, and an
operator-readable catalog of queue payloads and policies for the
dedicated-worker topology in [scaling](../../product/operator/scaling.md).

## Decisions

- **D1 Policy authority.** The document is authoritative for static options:
  each queue definition takes `options` from its generated channel constant.
  Options from operator configuration (the runs heartbeat window) and the runs
  job expiry stay in code and are described in the channel's `description`.
- **D2 Document split.** Two documents with explicit names. The WebSocket
  document's audience is client authors and its server is the HTTP origin;
  the queue document's server is the database.
- **D3 Strictness.** Required fields strict, unknown fields ignored (F4).
- **D4 NOTIFY.** Deferred: the case rests on the three variants without
  end-to-end coverage (F5).
