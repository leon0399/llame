# stdio MCP research — config surface, transport gaps, peer practice

Noncanonical research. Date: 2026-08-12. Scope: adding operator-configured
**stdio** MCP servers to the instance-scoped `mcpServers` map, alongside the
shipped Streamable HTTP transport. Transport, configuration surface, and
process lifecycle only.

This document does **not** reopen the authorization contract. Tool id form
(`mcp__<server>__<tool>`), the `tools.allowed` exact/wildcard filter, the
"operator attests read-only, remote annotations grant nothing" model,
drift-withdraws-the-tool, receipt/snapshot exactness, and redaction scope were
settled for HTTP in
[`2026-08-07-mcp-transport.md`](2026-08-07-mcp-transport.md) and the archived
`add-streamable-http-mcp-tools` change. stdio changes the transport, the
process lifecycle, and **where secrets live**; nothing above that line.

The read-only constraint stays an operator assumption with no new enforcement —
that was an explicit decision when this research was commissioned, not an
oversight. A capability/policy engine remains #133.

Method: read `@ai-sdk/mcp@1.0.67`'s shipped `src/` as installed in this repo's
sibling checkout, read `@modelcontextprotocol/sdk@1.29.0`'s compiled stdio
client for comparison, read llame's own MCP module for the integration points,
and surveyed four MCP-consuming products' documented stdio config surface. One
claim was settled by experiment (Node's rejection of an in-memory stream as a
`stdio` target, Finding 2) and one by observing a live process (Claude Code's
child environment, Finding 9); no MCP server was spawned for this document. See "what I could not
verify" for everything else that is source-read rather than exercised.

## Finding 0 — both motivating examples have an HTTP path; the case for stdio rests on the long tail

Recorded so the tradeoff is legible, not to relitigate it.

- **playwright-mcp** documents a long-running service variant binding a port
  (`--headless --browser chromium --no-sandbox`, port 8931 in the README's
  example), which llame's shipped `streamable-http` entry consumes today.
- **github-mcp-server** documents a GitHub-hosted remote at
  `https://api.githubcopilot.com/mcp/` (PAT or OAuth), described in its README
  as the easiest path.

So neither example is blocked by transport; both are blocked by _the operator
having to run and supervise a second process or trust a hosted endpoint_. The
decisive argument for embedding is the **long tail**: MCP servers that ship
stdio only and have no HTTP mode at all (the operator's own scripts, most
community filesystem/sqlite/notes servers). For those, the alternative is a
per-server bridge (`mcpo`, `supergateway`), which is the same supervision cost
multiplied by server count.

Corollary worth carrying into the proposal: **stdio does not unlock
playwright-mcp under the current policy.** Its catalog is `browser_click`,
`browser_navigate`, `browser_type`, `browser_evaluate`,
`browser_run_code_unsafe`, cookie/localStorage setters. Playwright annotates
each tool with a `readOnly` boolean, but llame's spec says remote annotations
grant nothing. Under "operator attests read-only," roughly the
`browser_snapshot` / `browser_console_messages` half is allowlistable.
github-mcp-server is the better exemplar because it ships an actual
`--read-only` flag plus `--toolsets` / `GITHUB_TOOLSETS` scoping
(`GITHUB_TOOLSETS` takes precedence over the flag, per its README).

## Finding 1 — the transport instance is the only guard seam, and the AI SDK's own stdio class is not the one to put in it

`@ai-sdk/mcp@1.0.67` exposes a second entry point, `./mcp-stdio`
(`package.json` `exports`), which exports the transport under an experimental
alias:

```
src/tool/mcp-stdio/index.ts:2   StdioMCPTransport as Experimental_StdioMCPTransport
```

`createMCPClient`'s option type is `transport: MCPTransportConfig | MCPTransport`
(`src/tool/mcp-client.ts:230`) and the constructor branches on
`isCustomMcpTransport(transportConfig)` (`:401-404`), assigning the instance
directly when one is passed. **llame can supply any `MCPTransport`.** This
matters because every guard llame currently enforces on the HTTP path lives
inside a wrapped `fetch` (`apps/api/src/mcp/mcp-server-client.ts:612-708`,
`protocolGuardedFetch` + `createMcpBoundedFetch`), and stdio has no `fetch` to
wrap. The transport instance is the only equivalent seam.

Which instance is the real question. Three candidates: `@ai-sdk/mcp`'s own
`Experimental_StdioMCPTransport`, the official SDK's `StdioClientTransport`,
or a llame-authored implementation. Finding 2 disqualifies the first; Finding 4
resolves the choice between the other two. Note that the AI SDK's published
documentation for this feature recommends the **official** SDK's class —
importing `StdioClientTransport` from `@modelcontextprotocol/sdk/client/stdio.js`
and passing the instance to `createMCPClient` — and mentions its own
`Experimental_StdioMCPTransport` only as an aliased alternative.

Confidence: high — read from installed source and the published docs page.

## Finding 2 — the shipped stdio transport is minimal; every llame HTTP guard needs a stdio counterpart built

`src/tool/mcp-stdio/mcp-stdio-transport.ts` is 157 lines.
`create-child-process.ts` is 21. Point-by-point against what llame enforces
today:

| llame HTTP guard                                                                                     | stdio counterpart in `@ai-sdk/mcp@1.0.67`                                                                                                                                                                                                                                                                                                                |
| ---------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 MiB bounded request/response (`mcp-server-client.ts:31,612-624`, `mcp-bounded-fetch.ts`)           | **none.** `ReadBuffer.append` (`mcp-stdio-transport.ts:124-129`) does `Buffer.concat` with no cap; `readLine` (`:131`) only yields on `\n`. A newline-less stdout stream grows llame's heap without bound.                                                                                                                                               |
| protocol pinned to `2025-03-26` / `2025-06-18` / `2025-11-25` (`mcp-server-client.ts:61-65,410-424`) | the library's own `SUPPORTED_PROTOCOL_VERSIONS` (`src/tool/types.ts:5-11`) additionally accepts **`2024-11-05`**, which llame excludes. Recoverable without interception: the client writes the negotiated version to `transport.protocolVersion` / `setProtocolVersion` (`mcp-client.ts:497-500`), so llame can gate on its own instance after connect. |
| 5s close deadline then abort (`mcp-server-client.ts:36,1036-1053`)                                   | `close()` is `this.abortController.abort()` and nothing else (`mcp-stdio-transport.ts:100-104`). The controller's signal is passed to `spawn` (`create-child-process.ts:13`), so Node kills the child with its default `killSignal` (`SIGTERM`) — **direct child only, no escalation, no process group.**                                                |
| session id treated as a protected value                                                              | not applicable; stdio has no sessions. Strictly simpler.                                                                                                                                                                                                                                                                                                 |
| secrets are header values, fed to `normalizeProtectedValues`                                         | secrets become **`env` values and `args`** (`--token=…`). Same machinery, different inputs. See Finding 3.                                                                                                                                                                                                                                               |
| nothing reaches logs                                                                                 | `stdio: ['pipe', 'pipe', config.stderr ?? 'inherit']` (`create-child-process.ts:11`). **Default `'inherit'` pipes the child's stderr into llame's process stderr** — a server that echoes a credential on a startup error writes it to the operator's logs. Not fixable from config: see below.                                                          |

**The `stderr` option looks like an escape hatch and is not one.**
`StdioConfig.stderr` is typed `IOType | Stream | number`
(`mcp-stdio-transport.ts:12`), which suggests handing the transport a stream
llame owns, bounds, and sanitizes. Node rejects that — an in-memory stream has
no underlying file descriptor:

```
$ node -e "spawn('sh',['-c','echo hi >&2'],{stdio:['pipe','pipe',new PassThrough()]})"
TypeError: The argument 'stdio' is invalid. Received PassThrough {...}
```

(Verified 2026-08-12 on Node v22.23.1.) A `Stream` here must be backed by a tty,
file, socket, or pipe fd. So with this transport the practical choices are
`'inherit'` (leak), `'ignore'` (no diagnostics at all, and there is deliberately
no MCP readiness endpoint, so logs are the operator's only channel), or a file
on disk — which is itself an unsanitized secret sink that llame would then have
to tail and clean up. The transport never exposes the child process, so there is
no way to read a `'pipe'`d stderr, and an unread pipe deadlocks the child at the
64 KiB pipe buffer. Finding 4 shows the official SDK solving exactly this.

**The process-tree claim, corrected.** The two motivating examples do spawn
trees, but they do not behave alike. `docker run -i --rm` attaches the CLI as a
client and the CLI forwards signals to the container, so SIGTERM to the direct
child is sufficient there. A directly invoked binary (`node /path/server.js`) is
a single process. The gap is specifically `npx`, whose signal forwarding to the
package's own child is unreliable. Combined with llame's unbounded reconnect
(`mcp-runtime.service.ts:24-25`, full jitter to a 5-minute cap), an `npx`-hosted
server that keeps dying could accumulate orphans — which is one more argument
for the crash-loop terminal state in Finding 6.

Confidence: high for what the source does and for the Node `stdio` rejection
(exercised). **Moderate** for the `signal`→`SIGTERM` default and for docker CLI
signal forwarding, both read from documented semantics rather than exercised.

## Finding 3 — the SDK default child environment is a fixed allowlist, which every consumer is free to override — and the choice determines whether redaction can work at all

`getEnvironment` (`src/tool/mcp-stdio/get-environment.ts:10-26`) builds the
child environment from a fixed, sudo-inspired allowlist plus whatever the
config declares:

```
POSIX:  HOME, LOGNAME, PATH, SHELL, TERM, USER
win32:  APPDATA, HOMEDRIVE, HOMEPATH, LOCALAPPDATA, PATH,
        PROCESSOR_ARCHITECTURE, SYSTEMDRIVE, SYSTEMROOT, TEMP,
        USERNAME, USERPROFILE
```

Values beginning with `()` are skipped (a shellshock-era function guard). The
official SDK has the byte-identical list plus `PROGRAMFILES`
(`@modelcontextprotocol/sdk/dist/esm/client/stdio.js:8-24`) — the two
implementations share ancestry.

**This is a default, not a constraint.** Both transports accept an `env` record,
and the official one merges it over the allowlist
(`env: { ...getDefaultEnvironment(), ...serverParams.env }`). A consumer that
wants full inheritance passes `{ ...process.env, ...declared }`, which is
exactly what Claude Code does — see Finding 9. So "allowlist" versus "inherit
everything" is a product decision each consumer makes, not something the library
imposes.

**Why it matters for the canonical github-mcp-server invocation.** The widely
copied form is:

```
docker run -i --rm -e GITHUB_PERSONAL_ACCESS_TOKEN ghcr.io/github/github-mcp-server
```

Bare `-e VAR` means "inherit `VAR` from my own environment," so the docker CLI
forwards it only if the variable exists in the child's environment. Under full
inheritance it does. Under the allowlist default it does not, and the server
starts unauthenticated. github-mcp-server's own README config works either way,
because it declares the value explicitly alongside the bare flag:
`"env": {"GITHUB_PERSONAL_ACCESS_TOKEN": "${input:github_token}"}`.

**The decision is load-bearing for redaction, and that is the argument that
should drive it — not trust.** A declared `env` value passes through llame's
`{env:…}`/`{path:…}` resolver, so the resolved secret is known to the process
and joins `normalizeProtectedValues` exactly as a header value does today
(`mcp-server-client.ts:587-590`). An inherited value never passes through the
resolver, so llame cannot strip it from the stderr channel that Finding 4 adds.
The concrete case is not hypothetical: a read-only Postgres MCP that fails to
connect prints its connection string to stderr, and under inheritance llame
would write `POSTGRES_URL` into operator logs. Under explicit declaration the
same value is protected and redacted out of that same line.

The secondary argument is economy. Full inheritance is only safe alongside a
deny-list of the parent's own secrets (Finding 9 shows Claude Code shipping
exactly that), so it costs an override plus a list to maintain. Explicit
declaration is the library default: pass the declared map and write nothing.

**llame's decision: explicit only.** The declared `env` map, unioned with the
SDK's base allowlist, is the complete child environment. Ambient inheritance is
not carried. Consequences accepted: `NODE_EXTRA_CA_CERTS`, `HTTPS_PROXY`,
`PLAYWRIGHT_BROWSERS_PATH` and similar need a one-line declaration, and a
`.mcp.json` entry copied from a tool that inherits may need one added. No
argument-sniffing rejection rule for bare `-e NAME` is needed or wanted — with
a declared `env` entry that form is the documented idiom.

Confidence: high — allowlist and merge order read from both SDKs' source;
the inheritance alternative verified against Claude Code in Finding 9.

## Finding 4 — the official SDK's `StdioClientTransport` closes the two gaps that matter, and a llame-authored transport is not justified

`@modelcontextprotocol/sdk@1.29.0`'s stdio client is the same lineage as the AI
SDK's copy — identical env allowlist, identical unbounded `ReadBuffer` — but its
public surface (`dist/esm/client/stdio.d.ts`) carries two accessors the AI SDK
version does not, and a real teardown sequence.

**Teardown** (`dist/esm/client/stdio.js:152-166`):

```
stdin.end()  →  race(close, 2s)  →  SIGTERM if exitCode === null
             →  race(close, 2s)  →  SIGKILL if exitCode === null
```

**Readable stderr**, which is the fix for Finding 2's unfixable leak:

```ts
/** ... If stderr piping was requested, a PassThrough stream is returned
    _immediately_, allowing callers to attach listeners before the start
    method is invoked. This prevents loss of any early error output. */
get stderr(): Stream | null;
get pid(): number | null;
```

The transport owns the PassThrough and pipes the child's stderr into it
internally (`stdio.js:97-98`), sidestepping the Node fd restriction entirely.
llame passes `stderr: 'pipe'`, attaches to `transport.stderr` before `start()`,
bounds it to a ring buffer, and runs it through the existing protected-value
sanitizer. That is precisely the policy llame needs, with no custom code.

| gap                | `@ai-sdk/mcp@1.0.67`        | official `StdioClientTransport`                                                                                                 | llame-authored                    |
| ------------------ | --------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | --------------------------------- |
| teardown ladder    | SIGTERM only, no escalation | **yes**                                                                                                                         | yes                               |
| readable stderr    | **no** (Finding 2)          | **yes** (`get stderr`)                                                                                                          | yes                               |
| bounded readbuffer | no                          | no — same unbounded `Buffer.concat` (`shared/stdio.js:5-24`)                                                                    | yes                               |
| process-group kill | no                          | no — `pid` is exposed, but the child is spawned without `detached`, so it is not a group leader and `kill(-pid)` does not apply | yes                               |
| protocol pin       | post-connect, either way    | same                                                                                                                            | same                              |
| cost               | zero                        | zero + a direct dependency                                                                                                      | ~200 lines, permanently diverging |

**Conclusion: adopt the official `StdioClientTransport`; do not author one.**
The two residual gaps do not justify a permanent fork of upstream code:

- The unbounded read buffer is a robustness concern against an
  operator-installed local process, not a remote attacker. It should be
  recorded as a known limitation, not solved by reimplementation.
- The tree-kill gap is narrower than it first appears (Finding 2's correction:
  docker forwards signals; a direct binary is one process; only `npx` is
  shaky), and the crash-loop terminal state in Finding 6 bounds the
  accumulation.

The cost is promoting `@modelcontextprotocol/sdk` from a transitive `shadcn`
dependency to a direct runtime dependency of `apps/api`, and running two MCP
implementations in one process. The AI SDK explicitly designs for this — its own
docs recommend the combination.

The interfaces are structurally compatible: `setProtocolVersion?` is optional on
both (`shared/transport.d.ts:87`, `mcp-transport.ts:86`), and the official
`close(): Promise<void>` satisfies `close(options?)`. Two integration details to
confirm with `tsgo` rather than assume: `send`'s options parameter is
`TransportSendOptions` on one side and `MCPTransportSendOptions` on the other,
and the official `Transport` does not declare `protocolVersion`, so the AI SDK
client assigns it dynamically (`mcp-client.ts:497-500`) and reading it back for
the protocol gate needs a narrow accessor type rather than a cast (`as unknown
as T` is banned repo-wide, #268).

Confidence: high for the transport surfaces and the recommendation; the TS
compatibility of `send` is **unverified** — see "what I could not verify."

## Finding 5 — llame's API process holds live MCP connections, so stdio children cannot be scoped to run-consuming processes

The attractive optimization — spawn children only where Runs execute — does not
work against the current architecture. `ChatsModule` imports `McpRuntimeModule`
(`apps/api/src/chats/chats.module.ts:3,34`) and `ChatLoopService` calls
`this.mcpRuntime.snapshotCandidates()` (`chat-loop.service.ts:137`) to author
the availability manifest when a Run is accepted. Discovery has no offline
form: the catalog _is_ a live connection.

```
        HTTP today                          stdio, same topology

  api-1 ─┐                          api-1 ── child ── (browser/container)
  api-2 ─┼──▶ one shared endpoint   api-2 ── child ── (browser/container)
  wkr-1 ─┤    scaled independently  wkr-1 ── child ── (browser/container)
  wkr-2 ─┘                          wkr-2 ── child ── (browser/container)
                                      ×  M configured servers
```

In the default co-located topology (`workers.all`, one process) this is 1 × M
and unremarkable. In a split topology it is (API processes + worker processes)
× M child processes, including on `web`-profile processes that never execute a
tool. This is a property of API-side snapshot authoring, not of stdio, but
stdio is where it becomes expensive. It belongs in `docs/scaling.md`.

Confidence: high — read from llame's own wiring.

## Finding 6 — three lifecycle semantics do not transfer from HTTP, and one concurrency property changes meaning

`docs/mcp-tools.md` "Runtime behavior" and
`apps/api/src/mcp/mcp-runtime.service.ts:22-26` define today's contract.

**a. Eager connect at boot → eager _spawn_ at boot.** For HTTP this is a socket.
For stdio it means a browser or container alive from process start regardless
of chat traffic. Lazy spawn looks like the fix but interacts badly with
Finding 5: the availability manifest is authored at Run-accept from the
process-local catalog, so a not-yet-spawned server is `unavailable` and the
_first_ Run emits an availability reminder and refuses the tool, succeeding
only on the second. **Eager is the semantically correct default**; the escape
hatch, if one is wanted, is an operator `enabled: false` switch (LibreChat's
`startup: false` is the same idea) rather than laziness.

**b. Reconnect-forever is wrong for a spawn.** `RECONNECT_BASE_MS` 1s doubling
to a `RECONNECT_CAP_MS` 5-minute cap with no attempt ceiling is correct for a
transient network outage and pathological for a typo'd `command`, a missing
image, or an `npx` package that does not exist — those respawn forever.

An earlier draft of this document proposed detecting that case with a fast-exit
heuristic (child exits within N seconds of spawn, K times consecutively →
terminal "misconfigured"). Finding 9 supersedes it: the reference implementation
has no crash-loop detector because it never loops, and separates transient from
configuration failures by **error class** rather than by timing. **llame's
decision: bounded retry — 5 attempts, 1s doubling, then terminal unavailable**,
with no fast-exit heuristic and no new `ToolUnavailableReason` variant. Because
llame processes run for weeks and there is no operator reinit surface, one cold
retry rides the existing 48–72 minute refresh tick, standing in for the manual
retry button a session-scoped tool can offer. **This applies to stdio only; the
shipped HTTP reconnect behavior is unchanged.**

**c. Catalog refresh should re-list, never recycle.** The 48–72 minute jittered
refresh is one `tools/list` on HTTP. Doing it by respawning the child would
turn a routine refresh into a browser restart. Re-listing on the live child is
correct, with the consequence that a stdio child lives for the whole process
lifetime — days — so its memory and file-descriptor growth becomes llame's
operational problem.

**d. Concurrency means something different.** One child per server per process,
shared by every concurrent Run in that process. JSON-RPC id multiplexing makes
this protocol-correct, and it is no different from HTTP (one client, one
session, shared). But for _stateful_ stdio servers the sharing is visible:
`workers.all.runs: 8` means eight Runs driving one browser, contending over
tabs and navigation state. Filesystem, sqlite, and search servers do not care.
Browser servers do. This is a documentation warning; per-Run server instances
would be a substantially larger design and are not recommended.

**e. `@latest` is a hidden network dependency.** `npx -y pkg@latest` fetches on
every spawn in every process: the catalog can change between two restarts of an
unchanged config (surfacing as declaration drift, which llame handles correctly
but confusingly), and boot on an air-gapped host fails at the fetch rather than
anywhere llame can explain. Docs should push pinned versions.

Confidence: high for the mechanics; the crash-loop thresholds (N seconds, K
attempts) are a proposal, not a finding.

## Finding 7 — the peer config surface has converged on `command` + `args[]` + `env{}`

The "how do others do it" question, from primary docs and generated types:

| product                          | `type`                                     | command shape                             | env                                     | secrets                                                                                | extras                                                                                                  |
| -------------------------------- | ------------------------------------------ | ----------------------------------------- | --------------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| **Claude Code** (`.mcp.json`)    | `"stdio"`, inferred when `command` present | `command` + `args[]`                      | `env{}`                                 | `${VAR}` and `${VAR:-default}`, expanded in `command`, `args`, `env`, `url`, `headers` | `timeout` (ms, per-tool-call); `MCP_TIMEOUT` env var for startup. `cwd` not documented on that page.    |
| **VS Code** (`mcp.json`)         | `"stdio"` **required**                     | `command` + `args[]`                      | `env{}` (string/number/null), `envFile` | `inputs[]` (`promptString` with `password: true`), referenced `${input:id}`            | `cwd`, `dev` (watch/debug), `sandboxEnabled` (macOS/Linux only)                                         |
| **opencode**                     | `"local"`                                  | `command: string[]` — **fused, no split** | `environment{}`                         | not surfaced in the config type                                                        | `cwd`, `enabled`, `timeout`                                                                             |
| **LibreChat** (`librechat.yaml`) | inferred                                   | `command` + `args[]`                      | `env{}`                                 | `${ENV_VAR}`; `customUserVars` for per-user credentials                                | `startup: false`, `chatMenu`, `serverInstructions`; `initTimeout`/`timeout` documented on HTTP examples |

Convergence is strong on **`command` + `args[]` + `env{}` (+ `cwd`)**.
opencode's fused `command: string[]` is the only dissent and the minority.

Implications for llame, given that README, `docs/mcp-tools.md`, and CHANGELOG
all advertise the `mcpServers` map as `.mcp.json`-compatible:

- Field names are effectively forced: `command`, `args`, `env`, `cwd`.
- **`type: "stdio"` should be explicit**, not inferred. Inference requires
  `oneOf` discrimination on property presence, which fights llame's
  strict-closed, `required: ["type", …]`, `additionalProperties: false` schema
  style — and Claude Code accepts explicit `"stdio"` too (its own
  `claude mcp add-json` emits it), so portability is unharmed.
- llame's existing `{env:…}` / `{path:…}` interpolation maps onto exactly the
  positions Claude Code expands `${VAR}` in. `{path:…}` is a better fit than
  VS Code's `envFile` for docker/k8s secret mounts.
- `inputs[]`, `envFile`, `dev`, and `sandboxEnabled` should be skipped. VS Code
  needs `inputs` because it prompts an interactive human; llame is a daemon
  with a resolver.
- `shell: false` is a security property, not a formatting convention: never
  accept a single-string command line.

Confidence: high for Claude Code, VS Code, and opencode (docs and generated
types read directly). **Moderate** for LibreChat — the fetched page did not
show `env` / `timeout` / `initTimeout` on a stdio example specifically, so
whether those fields apply to stdio entries is unconfirmed.

## Finding 8 — the products architecturally closest to llame declined embedded stdio

Context, deliberately overridden by this project's decision, but recorded
because it names the failure modes to design against.

- **Open WebUI** — self-hosted, multi-tenant, web-facing, i.e. llame's shape —
  supports only Streamable HTTP natively and ships [`mcpo`](https://github.com/open-webui/mcpo),
  a separate stdio→OpenAPI proxy. Its stated reason is that long-lived stdio
  connections are hard to maintain securely across users and sessions in a
  multi-tenant web app rather than a desktop process.
- **LibreChat** embeds stdio and documents it against itself: it "works well
  for local, single-user environments" and is "not scalable for remote or cloud
  deployments."
- **Docker MCP Gateway** supports stdio but recommends streamable HTTP for
  production, on the grounds that stdio "works for single-machine setups but
  breaks across container networks."

The self-hosted-personal-first deployment llame targets is exactly the case
these caveats do _not_ condemn: one host, one operator, co-located topology,
admin-authored config. The caveats bite in the split topology (Finding 5) and
in the supervision gaps (Findings 2 and 6), which is where the build effort
should go.

Docker-in-docker / docker-from-docker socket exposure was raised and

## Finding 9 — Claude Code is the reference implementation, and it settles env, stderr, timeouts, and retry

Read from the cached Claude Code source (`src/services/mcp/client.ts`,
`src/utils/subprocessEnv.ts`), corroborated by its published docs and, for the
environment question, by direct observation of a live child process.

**Transport** (`client.ts:12,950`) — the official `StdioClientTransport` from
`@modelcontextprotocol/sdk/client/stdio.js`. Independent confirmation of
Finding 4.

**Environment** (`client.ts:953-956`) — `env: { ...subprocessEnv(), ...serverRef.env }`,
where `subprocessEnv()` (`src/utils/subprocessEnv.ts`) returns `process.env`
verbatim (plus optional proxy variables). Full inheritance, declared values
overriding. Verified empirically rather than only read: `/proc/<pid>/environ` of
a running `context7-mcp` stdio child listed **75 variables**, including
`NGROK_AUTHTOKEN`, `SSH_AUTH_SOCK`, `GOPATH`, and the `WSL_*` set, plus an
injected `CLAUDE_PROJECT_DIR` — far beyond the six-name allowlist of Finding 3.

Inheritance ships with an **opt-in** deny-list (`CLAUDE_CODE_SUBPROCESS_ENV_SCRUB`)
removing `ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_AUTH_TOKEN`,
`ANTHROPIC_FOUNDRY_API_KEY`, `ANTHROPIC_CUSTOM_HEADERS`, the
`OTEL_EXPORTER_OTLP_*_HEADERS` family, `AWS_SECRET_ACCESS_KEY`,
`AWS_SESSION_TOKEN`, `AWS_BEARER_TOKEN_BEDROCK`,
`GOOGLE_APPLICATION_CREDENTIALS`, and `AZURE_CLIENT_SECRET`, each also in its
`INPUT_*` GitHub Actions form. The stated principle — _"claude re-reads these
per-request, subprocesses don't need them"_ — is sound, and it is the cost that
inheritance imposes. llame declines both (Finding 3): no inheritance, therefore
no deny-list.

**stderr** (`client.ts:957,966-983,1081-1083`) — `stderr: 'pipe'`, handler
attached _before_ connect so early startup output is not lost, accumulated to a
64 MiB cap, emitted as `logMCPError(name, 'Server stderr: …')` on failure paths
and then cleared to release the string. The inline rationale matches llame's:
_"prevents error output from the MCP server from printing to the UI."_ llame
adopts the same shape with a far smaller cap (64 KiB is ample for a diagnostic
tail) and the protected-value sanitizer in front of the log.

**Timeouts** (`client.ts:209-226,456-457,553`) — connect is
`MCP_TIMEOUT || 30_000`; tool calls are `MCP_TOOL_TIMEOUT || 100_000_000`
(~27.8 hours, effectively unbounded); the 60-second per-request timer is
HTTP/SSE only, explicitly not applied to stdio; the idle-abort window is 30
minutes for stdio against 5 for HTTP. Servers connect in batches
(`MCP_SERVER_CONNECTION_BATCH_SIZE || 3`) and do not block startup. **llame's
`DISCOVERY_DEADLINE_MS` is already 30s, so no change is required** — only an
operator override, expressed as a config field rather than an environment
variable, since llame's config-as-code rule keeps env out of settings except
through `{env:…}` tokens.

**Retry** — the published docs state it plainly and the source corroborates
(every reconnect path is keyed to SSE/HTTP concerns — session-404, SSE attempts
exhausted): an HTTP or SSE server that drops mid-session reconnects with
**up to five attempts, 1s doubling**, then is marked failed pending a manual
retry; an initial connection is retried **at most three times and only for
transient errors** (5xx, connection refused, timeout), never for authentication
or not-found, _"because they require a configuration change to resolve"_; and
**stdio servers are not reconnected automatically at all**. There is no
crash-loop detector because nothing loops.

**Type inference** (`client.ts:927,944,968`) — `serverRef.type === 'stdio' || !serverRef.type`:
an absent `type` means stdio. llame keeps `type` explicit (Finding 7) and
remains readable by this parser, which accepts the explicit form too.

**Catalog size is handled by a context-window-proportional threshold, not a
flat cap** (`src/utils/toolSearch.ts:104-108,731-733`, default at `:49`):

```ts
const contextWindow = getContextWindowForModel(model, betas);
const percentage = getAutoToolSearchPercentage() / 100; // default 10
return Math.floor(contextWindow * percentage);
// …
enabled: deferredToolTokens >= threshold;
```

Tool declarations above the threshold are deferred behind a search tool rather
than sent. The threshold is proportional, not a large-model exemption: a 1M
model gets roughly a 100k-token budget and still trips with a large enough
catalog — observed directly, since the session that produced this document ran
on a 1M model with tools deferred.

This is **out of scope for stdio** and recorded only because stdio makes large
catalogs much easier for an operator to acquire (`github-mcp-server --toolsets all`
is ~100 tools, `@playwright/mcp` ~60). It is orthogonal to the byte bounds in
Finding 2 and the requirement amendment this change makes: deferring
declarations changes what is _sent to the model_, not how many bytes are _read
from a server_. Tracked as
[#338](https://github.com/leon0399/llame/issues/338).

Confidence: high. Source-read with surviving identifiers, the environment claim
additionally verified against a live process.

## Does anything here reopen a prior decision?

No contract decision. The authorization model, tool id algorithm, allowlist
semantics, drift handling, and receipt/snapshot exactness are transport-
independent and stand unchanged. The read-only rule stays an operator
attestation with no new enforcement, by explicit decision.

What it does reverse is a set of **documented refusals**, which a proposal must
consciously undo rather than quietly branch around:

| artifact                                                        | what it says today                                                         |
| --------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `openspec/specs/mcp-tools/spec.md:26-29`                        | scenario: declaring stdio **fails schema validation**                      |
| `SPEC.md:99`                                                    | "sessionless MCP `2026-07-28`, deprecated HTTP+SSE, and stdio do not ship" |
| `VISION.md:156`                                                 | "local stdio MCP processes" listed under deliberate deferrals              |
| `apps/api/src/instance-config/llame.config.schema.json:75`      | the `type` enum description asserts no stdio                               |
| `apps/api/src/instance-config/config-loader.test.ts:505-506`    | a test asserting a stdio entry is rejected                                 |

| `apps/api/AGENTS.md`, `README.md`, `CHANGELOG.md`               | "no stdio fallback" phrasing                                               |

Plus one addition: `docs/scaling.md` should record that in a split topology
every process — including `web`-profile API processes — holds a child process
per configured stdio server (Finding 5).

## What I could not verify

- **No MCP server was spawned.** One narrow experiment was run (Node rejecting a
  `PassThrough` as a `stdio` target, Finding 2, Node v22.23.1); everything else
  about runtime behavior is source-read. Specifically unreproduced: Node's
  `spawn({ signal })` → default `killSignal` (`SIGTERM`), whether the docker CLI
  forwards that signal to the container, whether `npx` orphans its descendants,
  and whether the docker CLI forwards an undeclared `-e VAR` as unset. That last
  one no longer gates anything: llame declares `env` explicitly (Finding 3), so
  no rejection rule depends on it.
- Whether the official `StdioClientTransport` typechecks as an
  `MCPTransport` without adaptation. `send`'s options parameter is
  `TransportSendOptions` on one side and `MCPTransportSendOptions` on the other;
  the interfaces look structurally compatible and the AI SDK docs pair them
  explicitly, but this was not compiled under `tsgo`.
- Whether the official transport's 2s+2s teardown ladder fits inside llame's
  `SHUTDOWN_DEADLINE_MS` (5s, `mcp-runtime.service.ts:26`) once several servers
  close concurrently.
- Whether `waitForAbort(this.transport.close({ signal }), signal)` in
  `mcp-client.ts:515` reliably completes the abort before the race resolves —
  `StdioMCPTransport.close()` aborts synchronously on its first line
  (`:101`), which suggests it does, but this was not exercised against a hung
  child.
- LibreChat's stdio process model: whether servers are spawned once per
  instance or per user, and whether `env` / `initTimeout` / `timeout` apply to
  stdio entries. The fetched docs page shows those fields only on HTTP
  examples, and does not state the process model.
- Whether a later `@ai-sdk/mcp` patch on the `1.0.x` / `ai-v6` line changes any
  of Findings 1–4. Re-check the installed version before implementation if
  meaningful time has passed.
- Windows behavior throughout. Process groups, `detached`, and signal
  semantics differ materially; llame targets Linux and this research did not
  investigate the Windows path.
- Whether llame's existing per-call timeout and abort plumbing behaves
  identically over a stdio transport — assumed, since it lives above the
  transport interface, but not tested.
