# Model-chosen workspaces and skills from added roots

## Scope and method

This study asks whether the agent itself can select or change the workspace, rather than merely running commands inside a root selected by a person. A shell `cd` changes one process's current directory. It does not necessarily change the durable workspace binding, authorization scope, or owner-visible project identity. The comparison therefore treats only a first-class model-callable workspace operation as direct evidence of a workspace transition.

### What the positive cases show

The strongest direct precedent is a bounded state transition, not an instruction to run `cd`. llame specifies a single Chat binding, permission evaluation on each transition, canonical-path checks before binding, owner-only readback, persistence between Runs, and detach when the bound state becomes invalid. It does not make a Workspace a filesystem sandbox. [^llame-workspace-entry]

Paseo demonstrates a different boundary. An agent can create a workspace resource, including a managed worktree, and then create an agent in that workspace. Its tool contract does not prove that an existing caller can replace its own workspace binding. The UI and durable workspace record make the resource owner-visible. The source does not establish a separate confirmation dialog for the model tool. [^paseo-tools][^paseo-mcp]

For the remaining candidates, owner-selected task placement, model shell navigation, workspace creation, and workspace binding are distinct. Evidence that a harness launches in a worktree or accepts `cd` does not answer who owns a persistent root transition.

### Skill-source implications

Claude Code loads skills, legacy commands, and agents from a directory added with `--add-dir` or `/add-dir`. Permission-only extra directories do not load those resources. OpenCode and Codex have explicit skill-root configuration mechanisms separate from workspace membership. Gemini supports separately linking a path as a skill source. The docs do not say `/directory add` adds skill roots. oh-my-pi does not establish that workspace-root addition changes skill discovery.

Collision rules are product-specific. OpenCode uses later-source override by path-derived skill ID. Claude preserves added-directory duplicates under prefixes. Codex lists same-named skills without merging, but the reviewed docs do not settle which one an invocation selects. oh-my-pi retains differing variants under namespaces. Gemini resolves collisions by discovery tier and gives `.agents/skills` precedence over `.gemini/skills` within a tier.
