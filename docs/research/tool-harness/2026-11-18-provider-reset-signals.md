# Provider usage-limit and reset-time signals

## Summary

| Provider | Usage-window signal | Reset field + unit | Distinguishes billing cap? | Authoritative? |
| --- | --- | --- | --- | --- |
| Codex subscription (ChatGPT Responses) | HTTP 429; `error.code` = `usage_limit_reached` / `usage_not_included`; window headers at 100% | body `error.resets_at`, or `x-codex-primary/secondary-reset-at`: Unix epoch seconds | Yes, when body code identifies `insufficient_quota` / spend-cap codes; credits headers also expose overage | Yes for the named exhausted window's reset; not for a generic 429 with only an unexhausted window header |
| OpenCode Go (Zen gateway) | HTTP 429, nested error type `GoUsageLimitError`; `metadata.limitName` identifies 5-hour/weekly/monthly window | `Retry-After`: seconds-from-now (or HTTP-date per generic HTTP parser); no Go-specific absolute reset field | No reliable billing/overage discriminator from failure; Console's `Use balance` state is not exposed | No exact quota reset. `Retry-After` is a server delay hint, not documented as the window reset instant |
| Anthropic API | HTTP 429 `rate_limit_error`; Messages `error.details.error_code` distinguishes ramp vs enforced spend cap | `anthropic-ratelimit-*-reset`: ISO-8601 timestamp; `retry-after`: seconds-from-now (can be HTTP-date by HTTP convention) | Yes: `enforced_spend_limit_reached`; self-set spend cap can be 400 `invalid_request_error` | Yes for the specific rate-limit bucket reset header; no retry-after on tier spend cap and no machine-readable cap reset field |
| OpenAI API | HTTP 429 rate limit (`rate_limit_exceeded`, `slow_down`); reset headers name request/token bucket | `x-ratelimit-reset-requests/tokens`: duration text (e.g. `1s`, `6m0s`); `Retry-After`: seconds | Yes: `insufficient_quota`, `credit_balance_exhausted`, `organization_spend_limit_exceeded`, `project_spend_limit_exceeded` | Yes as a server-supplied duration for the specific rate-limit bucket; not a quota/billing reset signal |
| OpenRouter | HTTP 429 `rate_limit_exceeded`; 403 budget block; 402 credits/in-flight budget | budget `error.metadata.resets_at`: ISO-8601 UTC; `Retry-After`: seconds; key-management `X-RateLimit-Reset`: Unix epoch milliseconds | Yes: `limit_source` separates credits, in-flight, workspace/guardrail/key budget, rate limits | Yes for explicit budget `resets_at`; `Retry-After` is a minimum wait hint, not a usage window reset; no general inference quota reset header |

## Codex subscription (ChatGPT backend Responses)

**Failure shape.** The Responses failure carries an `error` object with machine-readable `code`, optional `message`, and in some cases `plan_type` and `resets_at`. Codex CLI recognizes `insufficient_quota`, `credit_balance_exhausted`, `organization_spend_limit_exceeded`, and `project_spend_limit_exceeded` as `QuotaExceeded`; `usage_not_included` is a distinct entitlement failure; `rate_limit_exceeded` and `slow_down` are throttles. The code path shown handles Responses failed events, so an HTTP status is not necessarily available in this event path. The subscription endpoint can return HTTP 429, but **the exact HTTP status for each Codex subscription `error.code` is not established by the inspected parser**. Do not infer body-code-to-status mapping from this source. [Codex CLI parser, `responses_error.rs` lines 26–104](https://github.com/openai/codex/blob/e58bf8f5233b51e7cd1679d947e3028c1ed91b06/codex-rs/codex-api/src/sse/responses_error.rs#L26-L104).

**Reset signals.** The backend supplies `error.resets_at` (Unix epoch seconds) for usage-window errors. Response headers can carry `x-codex-primary-used-percent`, `x-codex-primary-window-minutes`, `x-codex-primary-reset-at` and corresponding `secondary` fields. `used-percent` is percentage points; window minutes is minutes; `reset-at` is Unix epoch seconds. `x-codex-rate-limit-reached-type` is the type/name of the reached limit. `x-codex-credits-has-credits`, `x-codex-credits-unlimited`, and `x-codex-credits-balance` expose whether credits fund overage; these are not reset times. Codex CLI parses the window fields and credits explicitly. [Codex CLI header parser, `rate_limits.rs` lines 53–101, 180–230](https://github.com/openai/codex/blob/e58bf8f5233b51e7cd1679d947e3028c1ed91b06/codex-rs/codex-api/src/rate_limits.rs#L53-L101); [oh-my-pi parser, `response-handler.ts` lines 40–109](https://github.com/can1357/oh-my-pi/blob/de397d59d3aea002ebd2acb52ffeac64644f7cf7/packages/ai/src/providers/openai-codex/response-handler.ts#L40-L109).

A response with an explicit usage-limit code/reset is distinguishable from short throttling. For generic `rate_limit_exceeded` or bare 429, oh-my-pi uses only an error-level `resets_at` or a window whose `used_percent` is at least 100%; it deliberately does not turn an unspent window's reset into an hours-long throttle wait. With both windows exhausted, it takes the later reset. [oh-my-pi, `response-handler.ts` lines 67–93](https://github.com/can1357/oh-my-pi/blob/de397d59d3aea002ebd2acb52ffeac64644f7cf7/packages/ai/src/providers/openai-codex/response-handler.ts#L67-L93).

**Assessment.** Treat provider-originated epoch `resets_at` as authoritative for the limit it names. A reset alone does not prove the account is blocked: combine it with the code and exhausted-window verdict. Credits/overage state can keep a reached plan window usable, and spend cap state is a separate meter. oh-my-pi's usage implementation parses `spend_control.individual_limit.reset_at` as epoch seconds and `reset_after_seconds` as a relative duration; it also parses `spend_control.reached` and credits separately. [oh-my-pi, `usage/openai-codex.ts` lines 243–304, 307–343, 381–390](https://github.com/can1357/oh-my-pi/blob/de397d59d3aea002ebd2acb52ffeac64644f7cf7/packages/ai/src/usage/openai-codex.ts#L243-L304).

## OpenCode Go (Zen gateway)

**Failure shape.** llame's accepted gateway contract documents a 429 with body type `GoUsageLimitError`, plus a `retry-after` header. Metadata names workspace and limit; the known limits are five-hour, weekly, and monthly. llame has not observed this error in its cited live proof, and its own spec explicitly leaves whether monthly exhaustion instead uses a 401 `MonthlyLimitError` unverified. Treat 429/`GoUsageLimitError` as documented gateway behavior, not a universally verified status mapping. [llame operator record, lines 156–168, 191–200](https://github.com/leon0399/llame/blob/master/docs/product/operator/providers/opencode-go.md#L156-L200).

OpenCode itself recognizes typed quota codes including `gousagelimiterror` and `budgetlimiterror` separately from generic throttle detection; its classifier considers 402 a quota failure and 429 a quota failure only when the code/message carries quota wording. [OpenCode `provider-error.ts` lines 89–100, 141–160, 216–263](https://github.com/anomalyco/opencode/blob/cdd0585e048b08d85df1f854b7deb3fa52b8dac4/packages/ai/src/provider-error.ts#L89-L100). For the Go-specific UI, it parses only `metadata.workspace` and `metadata.limitName` from the raw body, then computes its displayed reset by adding `retryAfterMs` to event creation time. [OpenCode `go-limit-tray.tsx` lines 15–35](https://github.com/anomalyco/opencode/blob/cdd0585e048b08d85df1f854b7deb3fa52b8dac4/packages/app/src/session/composer/go-limit-tray.tsx#L15-L35); [reset calculation, `usage-exceeded-dialogs.tsx` lines 21–54](https://github.com/anomalyco/opencode/blob/cdd0585e048b08d85df1f854b7deb3fa52b8dac4/packages/app/src/session/usage-exceeded-dialogs.tsx#L21-L54).

The general OpenCode HTTP parser accepts `retry-after-ms` as milliseconds, numeric `Retry-After` as seconds, or an HTTP-date; it normalizes all of these to milliseconds. [OpenCode `executor.ts` lines 37–51](https://github.com/anomalyco/opencode/blob/cdd0585e048b08d85df1f854b7deb3fa52b8dac4/packages/ai/src/route/executor.ts#L37-L51). llame's spec and runbook describe Go's header as `retry-after` but expose no absolute reset field. [llame spec, lines 217–221](https://github.com/leon0399/llame/blob/master/openspec/specs/opencode-go-provider/spec.md#L217-L221); [runbook, lines 156–168](https://github.com/leon0399/llame/blob/master/docs/product/operator/providers/opencode-go.md#L156-L168).

**Assessment.** Typed error and `limitName` distinguish usage window from ordinary short throttle; neither establishes exact reset. `Retry-After` is the gateway's retry delay recommendation and OpenCode displays it as an estimated reset, but no primary source inspected states that it equals the account's canonical five-hour/weekly/monthly reset. The gateway's separate “Use balance”/overage setting is not conveyed in the error contract, so the failure alone cannot tell an operator whether a subscription window or billing/balance condition is fixable by waiting. The exception shape of an alternate `MonthlyLimitError` remains unverified.

## Anthropic API

**Failure shape.** Normal rate limits return HTTP 429 and `error.type: rate_limit_error`. The response's `anthropic-ratelimit-requests-*`, `anthropic-ratelimit-input-tokens-*`, and `anthropic-ratelimit-output-tokens-*` headers report limit/remaining/reset for each dimension; reset values use ISO-8601 instants. `retry-after` provides a seconds-from-now delay when returned. API docs describe limits as token-bucket replenishment, not fixed intervals, and say to wait at least the delay in `retry-after` when present. [Anthropic rate-limit docs](https://docs.anthropic.com/en/api/rate-limits#about-rate-limits).

**Usage cap vs throttle.** Anthropic distinguishes rate-limit 429 from monthly tier spend cap through `error.details.error_code: enforced_spend_limit_reached`; that 429 has no `retry-after`, and the message states access resumes on the first of next month at 00:00 UTC. A user-set org/workspace spend limit returns HTTP 400 `invalid_request_error`, with a message stating when access resumes; a Claude Code workspace cap is an exception and may be 429 with `retry-after`. A ramp limit is still 429 but Messages `error.details.error_code: ramp_limit_exceeded`. [Anthropic rate-limit docs, spend cap and ramp-limit sections](https://docs.anthropic.com/en/api/rate-limits#reaching-your-spend-cap); [Anthropic errors docs](https://docs.anthropic.com/en/api/errors#http-errors).

**Assessment.** The `anthropic-ratelimit-*-reset` for the limit bucket that is exhausted is a precise provider timestamp and can anchor quota wait. Do not treat `retry-after` as a monthly spend-cap reset: it is absent on the tier cap and may not be an absolute instant. Cap resumption is documented in prose but not as a stable structured reset field.

## OpenAI API

**Failure shape.** HTTP 429 can mean a temporary request/token limit, rapid traffic ramp (`rate_limit_error` + `slow_down`), exhausted prepaid credits (`credit_balance_exhausted`), organization/project spend cap (`organization_spend_limit_exceeded` / `project_spend_limit_exceeded`), or assigned organization usage cap (`organization_usage_limit_exceeded`). `error.type` alone is not sufficient; inspect `error.code`. [OpenAI error-code docs](https://developers.openai.com/api/docs/guides/error-codes#api-errors).

**Reset signals.** `x-ratelimit-limit-requests/tokens` and `x-ratelimit-remaining-requests/tokens` are counts. `x-ratelimit-reset-requests/tokens` are time-until-reset duration values (e.g. `1s`, `6m0s`), not epoch timestamps. `Retry-After` is minimum seconds to wait for temporary rate limiting when present. [OpenAI rate-limit guide, “Rate limits in headers”](https://developers.openai.com/api/docs/guides/rate-limits#rate-limits-in-headers). The OpenAI error guide warns that billing/spend/quota errors will not recover by retrying and must be addressed by changing balance/limits. [OpenAI error-code docs](https://developers.openai.com/api/docs/guides/error-codes#429---credit-balance-exhausted).

**Assessment.** For a 429 identified as short rate-limit/`slow_down`, reset duration fields are provider-supplied timing for the request/token bucket and usable as a wait signal. They do not distinguish fixed usage window exhaustion from ramp throttling by themselves, nor authorize waiting out credits/spend/assigned usage caps. Those caps are distinguishable from error code, but no specific cap reset field is supplied in the cited API docs.

## OpenRouter

**Failure shape.** The body is `{error: {code, message, metadata?}}`, with HTTP status normally matching `error.code` before output starts. The documented meanings include 402 credit exhaustion, 403 permission/budget blocks, and 429 platform/upstream rate limiting; mid-stream failures arrive in an SSE/body error while HTTP remains 200. [OpenRouter error docs](https://openrouter.ai/docs/api/reference/errors-and-debugging#errors).

A 429 usually carries `error.metadata.error_type: rate_limit_exceeded`; upstream errors may also include `provider_code`. `Retry-After` is standard seconds on 429/503 and 402 in-flight-budget cases. It may represent the minimum delay, not a durable monthly/window reset. [OpenRouter error docs, Retry-After and provider errors](https://openrouter.ai/docs/api/reference/errors-and-debugging#retry-after-header).

**Spend and credits.** On 402, `error.metadata.limit_source` distinguishes `openrouter_in_flight_budget` (transient; can include `Retry-After`), `openrouter_credits` (balance or one-request cost; not solved by waiting), and `openrouter_key_limit`. Budget caps can fail 403 with `limit_source` identifying guardrail, workspace, or key limit and `metadata.resets_at` as ISO-8601 UTC, or null for lifetime budgets. The same budget objects appear in `GET /api/v1/key` as `budgets` and `effective_budget`; fields include `reset_interval`, `resets_at`, and USD spend/remaining. [OpenRouter limits docs, credit limits and budget limits](https://openrouter.ai/docs/api_reference/limits#credit-limits); [error examples, 402/403](https://openrouter.ai/docs/api/reference/limits#handling-403-budget-errors).

**Assessment.** For a budget rejection with a non-null `metadata.resets_at`, OpenRouter supplies an exact reset instant that is authoritative for that named spend budget. For an in-flight spending budget, follow `Retry-After` as a transient wait recommendation. Generic inference 429s do not expose an absolute reset time in the docs reviewed. `X-RateLimit-Reset` is documented as Unix epoch milliseconds only for key-management daily-limit errors, not for inference usage windows; do not generalize it to inference requests. Free-model daily request counters are exposed by `GET /api/v1/key`, but that endpoint gives counts/UTC day policy rather than an error reset timestamp.

## Consequences for quota wait

1. **Codex subscription: yes**, when a usage-limit error or exhausted primary/secondary window supplies `resets_at` / `x-codex-*-reset-at`; parse it as epoch seconds and respect the specific reached-window verdict. Do not infer from a 429 plus an unexhausted window.
2. **OpenCode Go: no authoritative reset instant is established.** `Retry-After` can support a bounded wait hint, but Go documents no absolute reset and OpenCode's displayed reset is derived from that delay. Do not model it as a canonical window reset without stronger gateway evidence.
3. **Anthropic: yes for rate-limit buckets**, using the exhausted bucket's `anthropic-ratelimit-*-reset` ISO timestamp; `retry-after` is a delay hint. No structured authoritative reset is available for tier spend-cap 429s.
4. **OpenAI API: yes for temporary bucket throttling**, using the `x-ratelimit-reset-*` duration (or `Retry-After`); code must exclude credit, spend, and assigned usage caps, which need operator/account action and have no cited reset field.
5. **OpenRouter: yes for explicit spend budgets** with non-null `error.metadata.resets_at`; `Retry-After` can guide temporary 429/in-flight-budget waiting. Generic inference 429s and credit exhaustion have no authoritative reset signal.
