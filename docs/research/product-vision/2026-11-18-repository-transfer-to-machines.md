# Repository transfer to provisioned Machines

## Summary

**Finding (moderate confidence):** keep reusable forge credentials at the llame authority and make publish-back an explicit accepted operation. For the current GitHub-centered case, the best default to investigate is a GitHub App installation token minted on demand, narrowly limited to the selected repository and Contents permission, exposed only through a daemon-mediated credential-helper request while Git runs. This avoids installing a long-lived private key on the guest, but the short-lived token is still usable by a compromised guest until it expires or is revoked. The stricter alternative is to transfer a Git object pack/bundle into an llame-owned repository and return the resulting objects/ref over the daemon protocol; it removes forge authority from the guest, but requires llame to own LFS, submodule and publish reconciliation semantics. This comparison is a design inference, not an implemented llame capability. [^github-installation-token][^github-credential-types][^git-bundle]

This note answers the transfer and credential question only. The existing llame direction already distinguishes registered Workspaces from disposable Sandboxes, recommends staged immutable result refs followed by explicit acceptance, and records the loss window when a box dies before reconciliation. See [OpenClaw sandboxes and cloud workers](2026-09-27-openclaw-sandboxes-and-cloud-workers.md#f6-the-workspace-goes-to-the-executor-and-comes-back-per-turn) and [multi-device execution placement §4.6](2026-10-18-multi-device-execution-placement.md#46-ephemeral-sandboxes); those mechanics are not repeated here. [^git-bundle]

### Transfer and publish-back boundary

For llame, transfer should not imply direct final publication. On provision, the authority resolves the owner-scoped Repository/Checkout record to a pinned commit and sends only the selected contents. The Machine may create commits; on return it submits objects plus a proposed ref/update. llame stages that immutable result, reports the ref and unsynced state, then requires explicit acceptance before updating a trusted checkout or pushing outward. This follows the existing staged/accepted-ref decision in [§4.6 of the execution placement research](2026-10-18-multi-device-execution-placement.md#46-ephemeral-sandboxes), rather than introducing a second publish model. **Inference from current research direction; not a shipped protocol.**

A credential-brokered push is operationally simpler and handles standard Git remote operations, but it makes the guest a forge principal during the token window. A no-forge-credential transfer path offers the stronger containment boundary, but Git transport is only one part of the lifecycle: include LFS payload transfer and explicitly resolve submodules or report them unavailable. Avoid silently treating pointers or submodule gitlinks as complete content. [^github-lfs][^git-submodule]

## Evidence limits

This is a documentation comparison, not a test of live Git-provider behavior or a design review of Forgejo/Soft Serve. Current llame's provisioned Machine transfer protocol is not specified here. Token scopes vary by provider and by user/installation configuration; the GitHub figures are GitHub-specific. The reviewed Codespaces security page describes automatic token expiry but does not give a precise duration. Prior llame research owns staged-result and loss-window conclusions; this report links to it rather than repeating its evidence. [^codespaces-security]
