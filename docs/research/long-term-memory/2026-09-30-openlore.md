# OpenLore: a governed Markdown server, not a memory system

Surveyed 2026-09-30. Noncanonical: evidence and transfer ideas, not a decision.

Source is [aakarim/OpenLore](https://github.com/aakarim/OpenLore) at
[`2c7b60c0`](https://github.com/aakarim/OpenLore/tree/2c7b60c08e4b99f16681101b7700af288f70ac46)
(`v0.7.1-24`, 2026-09-29), Go, Apache-2.0. The history runs from 2026-04-14 with
about 180 commits, almost all by one author, and 174 `*_test.go` files. This is a
quick read of the documentation and the write-path source; nothing was built or
run, and the MCP session lifetime and multi-process behavior were not traced.

## Summary

OpenLore serves a directory of Markdown to agents through an in-process Go shell
(`ls`, `cat`, `grep`, `find`, `jq`, pipes) over SSH, SFTP, MCP and a web
dashboard. Each identity sees only the docsets granted to it. The README
advertises it as a "continuous learning repository" and "shared live memory for
teams of agents"
([README L100–L106](https://github.com/aakarim/OpenLore/blob/2c7b60c08e4b99f16681101b7700af288f70ac46/README.md#L100-L106)),
but the product has no extraction, consolidation, ranking, recall injection or
forgetting semantics: "There is no ingestion pipeline, vector database or LLM
required"
([README L22](https://github.com/aakarim/OpenLore/blob/2c7b60c08e4b99f16681101b7700af288f70ac46/README.md#L22)).
The "learning" is whatever agents choose to write and later `grep`.

It therefore sits beside llame's Knowledge Spaces and the planned Profile Space,
not the `memory_facts` layer of the [cross-report](./2026-07-05-memory-landscape/CROSS-REPORT.md).
Its value to llame is the write path: automatic compare-and-swap on blind
overwrites, admission rules with growth caps, a create-only inbox grant, and a
principal/actor attribution split. Retrieval, lifecycle and tenancy offer
nothing llame lacks.

## Mechanics

**M1 — One write seam, whole-file atomic swaps.** Every mutating verb (`>`,
`>>`, `tee`, `sed -i`, `patch`, `mv`, `publish`, `spawn` write-back) funnels
through `cmds.WriteFile`/`WriteFileCAS` into `WriteFileAtomic(path, bytes,
precondition)`: temp file, `fsync`, `rename(2)`, under a lock that also checks
the precondition. There are no partial or streamed writes; append and patch are
read-modify-write of the whole file
([write-system.md L14–L40](https://github.com/aakarim/OpenLore/blob/2c7b60c08e4b99f16681101b7700af288f70ac46/docs/write-system.md#L14-L40),
[L73–L89](https://github.com/aakarim/OpenLore/blob/2c7b60c08e4b99f16681101b7700af288f70ac46/docs/write-system.md#L73-L89)).
SFTP stages offset writes privately and submits one whole-file write on close
([SECURITY.md L68–L73](https://github.com/aakarim/OpenLore/blob/2c7b60c08e4b99f16681101b7700af288f70ac46/SECURITY.md#L68-L73)).

**M2 — Session read-tracking makes blind overwrites compare-and-swap.** A
per-session wrapper records the SHA-256 of every file the session reads and
re-records it after each successful write. Under the default `hash` policy, a
blind overwrite uses the last-read hash as `IfMatch`, so it fails if the file
changed since the session saw it; an untracked path falls back to the
command-time read or create-only. Append and `patch` are always CAS
([write-system.md L105–L169](https://github.com/aakarim/OpenLore/blob/2c7b60c08e4b99f16681101b7700af288f70ac46/docs/write-system.md#L105-L169),
[read_tracking_fs.go L26–L102](https://github.com/aakarim/OpenLore/blob/2c7b60c08e4b99f16681101b7700af288f70ac46/pkg/openlore/read_tracking_fs.go#L26-L102),
[server.go L1091–L1101](https://github.com/aakarim/OpenLore/blob/2c7b60c08e4b99f16681101b7700af288f70ac46/pkg/openlore/server.go#L1091-L1101)).
The tracked state is in memory and dies with the session.

**M3 — Layered per-session gates.** Outermost first: capability-gated verb
(`read`/`write`/`publish`/`spawn`/`admin`; a disallowed verb behaves as if it
does not exist), a scope gate confining writes strictly inside the identity's
docset roots, a plugin admission chain that may allow, defer or reject, and a
single serialized write log before the substrate
([write-system.md L202–L263](https://github.com/aakarim/OpenLore/blob/2c7b60c08e4b99f16681101b7700af288f70ac46/docs/write-system.md#L202-L263)).
Write authorization is resolved against current policy on every operation, not
the session snapshot
([server.go L1070–L1082](https://github.com/aakarim/OpenLore/blob/2c7b60c08e4b99f16681101b7700af288f70ac46/pkg/openlore/server.go#L1070-L1082)).

**M4 — Folder rules at admission, including growth caps.** Declarative rules
(`size/lines`, `okf`, `link/resolves`, …) layer from `lore.json` and
`.lore/config.yaml`; child folders can only add or tighten
([folder-rules.md L1–L51](https://github.com/aakarim/OpenLore/blob/2c7b60c08e4b99f16681101b7700af288f70ac46/docs/folder-rules.md#L1-L51)).
`max: initial` caps a file at its first admitted size times `growth` (default
1.25). The baseline is append-only, names the actor who set it, and can only be
reset by a `config.edit` role, with an audit record. A rejection names the rule,
the numbers, a concrete remedy ("move the new material into a sibling file …
and add a link") and the override
([folder-rules.md L194–L293](https://github.com/aakarim/OpenLore/blob/2c7b60c08e4b99f16681101b7700af288f70ac46/docs/folder-rules.md#L194-L293)).
The `okf` rule validates Open Knowledge Format concepts on every write
([rules-stdlib.md L23–L38](https://github.com/aakarim/OpenLore/blob/2c7b60c08e4b99f16681101b7700af288f70ac46/docs/rules-stdlib.md#L23-L38)).

**M5 — `publish` is a create-only inbox grant.** A `publish` role reads the
whole docset but writes only inside its configured inbox folder, and cannot
overwrite or delete; `rw` is needed to maintain existing documents
([publish-to-inbox.md L5–L70](https://github.com/aakarim/OpenLore/blob/2c7b60c08e4b99f16681101b7700af288f70ac46/docs/publish-to-inbox.md#L5-L70)).
Promotion out of the inbox is manual; the bundled housekeeping skill only flags
items older than seven days
([openlore-housekeeping SKILL.md L42–L51](https://github.com/aakarim/OpenLore/blob/2c7b60c08e4b99f16681101b7700af288f70ac46/assets/skills/agents/shellm/openlore-housekeeping/SKILL.md#L42-L51)).
Middleware can also defer a write as `pending as <ref>`, but core stores no
pending changes
([write-system.md L267–L280](https://github.com/aakarim/OpenLore/blob/2c7b60c08e4b99f16681101b7700af288f70ac46/docs/write-system.md#L267-L280)),
and in this revision only tests call `op.Pending`.

**M6 — Attribution separates principal from actor.** Each commit carries
`Principal`, `Actor`, `ActorKind` and client-auth level, stored beside the
content-addressed change set rather than inside it
([middleware.go L9–L28](https://github.com/aakarim/OpenLore/blob/2c7b60c08e4b99f16681101b7700af288f70ac46/pkg/openlore/middleware.go#L9-L28)).
OAuth delegation puts the human in `sub` and the client in the RFC 8693 actor
claim, so a write reads as `adil/claude@claude.ai`; a delegate can hold no more
authority than its principal
([mcp.md L195–L200](https://github.com/aakarim/OpenLore/blob/2c7b60c08e4b99f16681101b7700af288f70ac46/assets/lore/mcp.md#L195-L200)).

**M7 — History is a journal, not version control.** A `HistoryRecord` holds
commit id, time, attribution, file key, action and content hash, sharded as
JSONL per file
([history.go L25–L73](https://github.com/aakarim/OpenLore/blob/2c7b60c08e4b99f16681101b7700af288f70ac46/pkg/openlore/history.go#L25-L73)).
Stored blobs (default on) let `history` show diffs, with optional retention
([openlore-yml.md L457–L487](https://github.com/aakarim/OpenLore/blob/2c7b60c08e4b99f16681101b7700af288f70ac46/docs/openlore-yml.md#L457-L487)).
The dashboard timeline "does not promise historical bodies, diffs, or
restoration"
([dashboard.md L120–L122](https://github.com/aakarim/OpenLore/blob/2c7b60c08e4b99f16681101b7700af288f70ac46/docs/dashboard.md#L120-L122)),
and no revert command was found.

**M8 — Read telemetry as a hygiene signal.** The dashboard reports per-file
bytes, lines and token estimates against a chosen context window, most- and
least-read files and lines, and human/agent/unknown attribution. It is
best-effort: buffered events can be lost on a crash
([dashboard.md L87–L113](https://github.com/aakarim/OpenLore/blob/2c7b60c08e4b99f16681101b7700af288f70ac46/docs/dashboard.md#L87-L113)).

## Claims versus code

- **D1 — `SECURITY.md` describes an older product.** It says `publish` is the
  only write path, that any authenticated identity can publish to any writable
  docset, and that there is no audit trail
  ([SECURITY.md L207–L229, L268–L281](https://github.com/aakarim/OpenLore/blob/2c7b60c08e4b99f16681101b7700af288f70ac46/SECURITY.md#L207-L281)).
  The write-system document and source describe `rw` verbs, per-identity scope
  gates and a commit journal (M3, M7). Evaluate the security posture from source,
  not that file.
- **D2 — "No process execution" holds for session commands only.** Operator
  `shellexec` hooks run `sh -c` before reads, before commits and after writes,
  and identities granted `spawn` run `sh -c` jobs whose output is written back
  ([write-system.md L290–L331](https://github.com/aakarim/OpenLore/blob/2c7b60c08e4b99f16681101b7700af288f70ac46/docs/write-system.md#L290-L331)).
  Spawn jobs are in memory and lost on restart.
- **D3 — Permissive defaults.** Built-in defaults accept keyless SSH with
  `unknown_identity: allow`
  ([config.go L780–L787](https://github.com/aakarim/OpenLore/blob/2c7b60c08e4b99f16681101b7700af288f70ac46/internal/config/config.go#L780-L787)).
  The substrate boots read-only and the CLI calls writes "experimental"
  ([main.go L635](https://github.com/aakarim/OpenLore/blob/2c7b60c08e4b99f16681101b7700af288f70ac46/cmd/openlore/main.go#L635)),
  yet the embedded `assets/config/openlore.yml`, whose token issuer is the hosted
  `openlore.sh`, sets `readonly: false`
  ([openlore.yml L20–L24](https://github.com/aakarim/OpenLore/blob/2c7b60c08e4b99f16681101b7700af288f70ac46/assets/config/openlore.yml#L20-L24)).
- **D4 — Isolation is application-layer.** Docset scoping is enforced by the
  Go VFS wrappers over one host directory tree. That is adequate for a single
  trusted operator; it is not a datastore-enforced tenant boundary.

## Transfer to llame

- **T1 — Close the blind-replace gap before the Profile Space ships.** Native
  `write` with `replace: true` replaces an existing file with no precondition
  ([native-file-tools spec L802–L808](../../../openspec/specs/native-file-tools/spec.md)).
  #212 dropped commit-time CAS on the grounds that "correction safety lives in
  native `edit`'s exact-match mutation fence", but `write` bypasses that fence.
  Once a user edits `USER.md` through Git while an agent works from an earlier
  read, a replace silently discards the user's change. OpenLore's M2 fixes this
  without a hash parameter: record the content hash of every `kb://` read in the
  Run attempt and make a replace fail if the current hash differs. The state
  must survive worker resume, which OpenLore's in-memory map does not need to.
  Moderate confidence this matters: rare with one writer, normal once humans and
  agents share Profile files. Tracked in
  [#706](https://github.com/leon0399/llame/issues/706), which chose an explicit
  read-issued tag over implicit tracking because the tag lives in the stored
  tool result and needs no per-Run state.
- **T2 — Growth caps with an actionable rejection for standing-context files.**
  `max: initial` (M4) is a direct answer to the bloat the OMP study measured,
  where about 73% of captured lessons never reached the prompt
  ([omp-memory O5](./2026-09-28-omp-memory.md)). For #513, enforce a size or
  token cap on agent-authored changes to `USER.md`, `SOUL.md` and `AGENTS.md`
  in trusted code, report the numbers and a remedy (split into a linked sibling
  or summarize), and let only the owner raise the cap. The cap must not live in
  a model-editable file.
- **T3 — Record principal and actor separately.** M6 matches what #212 needs:
  principal = owner, actor = Run (chat, model, attempt), kept in the Run record
  rather than in commit content. #212 already excludes commit trailers, which
  agrees with keeping attribution outside the change set.
- **T4 — A create-only lane is the cheapest review-before-accept.** M5 gives an
  untrusted writer new files only, in one folder, with promotion left to the
  owner. For Profile Space changes, which #513 says must not become accepted
  state unreviewed, this is a file-level alternative to the deferred candidate
  refs (#212's D5). Do not cite OpenLore's `Pending` seam as prior art for a
  review queue: nothing in core implements it.
- **T5 — Read telemetry as a hygiene input, later.** M8's least-read files and
  token-versus-window view are the usage signal the cross-report wants for
  ranking and pruning. llame already stores every `kb://` read in tool parts, so
  "never read in N days" is derivable without new capture. Not needed before
  the Profile Space works.

Rejected:

- **R1 — Connecting OpenLore as an operator MCP server for personal memory.**
  llame's MCP servers are instance configuration, so every user would share one
  OpenLore identity and see the same docsets, which breaks owner isolation.
  OpenLore tokens are short-lived with refresh
  ([mcp.md L115–L135](https://github.com/aakarim/OpenLore/blob/2c7b60c08e4b99f16681101b7700af288f70ac46/assets/lore/mcp.md#L115-L135)),
  which static `headers` cannot renew. Acceptable only as a read-only, shared
  team-docs source, the use case ROADMAP defers to shared Knowledge Spaces.
- **R2 — An in-process virtual shell.** llame already has selector `read`,
  literal search and allowlisted host `bash`. A second command interpreter would
  duplicate those surfaces.
- **R3 — A journal instead of Git.** M7 records who wrote what but promises no
  restoration. llame's plan to make Git the recovery path is stronger and should
  stay.

## Method and limits

Read the README, `SECURITY.md`, the write-system, folder-rules, inbox,
dashboard and MCP documents, the bundled agent skills, and the write-path source
files cited above at the pinned revision. Not traced: whether an MCP `shell`
call reuses a session (which decides whether M2's read tracking spans MCP
calls), multi-process deployment of the single write log, and the analytics
pipeline. No build, test or benchmark was run.
