# beads (`bd`) — deep-dive notes (2026-07-09)

Source: <https://github.com/gastownhall/beads> at commit `2f778fa8c6d87ccaa894307d348651c08db57c81` (2026-07-09; cloned same day to a local read-only checkout — file:line references below are against that commit) — Steve Yegge's beads (Go module still `github.com/steveyegge/beads`; repo moved to the `gastownhall` org at v1.0.0). Go, ~464k LOC, ~52% test-file ratio, 15 CI workflows, 114 tagged releases in ~9 months (2025-10 → 2026-07). Storage is **Dolt** (MySQL-compatible versioned SQL DB), not JSONL/git-native; `.beads/issues.jsonl` is an interchange/portability artifact, not the source of truth. A serious, actively engineered project whose README framing — "persistent, structured memory for coding agents… replaces messy markdown plans with a dependency-aware graph" — makes it _working memory for long-horizon tasks_, an issue graph rather than episodic/semantic memory in our sense. Its long-term-memory feature (`bd remember`) is a small afterthought (§4). So beads feeds llame's **goals/todos/runs** design far more than SPEC §20 memory, with one adopted micro-pattern and two anti-examples for the memory chapter.

## 1. Dependency model with readiness semantics

Four dependency types, split by whether they gate readiness (`docs/ARCHITECTURE.md:196-202`):

| type              | readiness effect | semantics                                                                                  |
| ----------------- | ---------------- | ------------------------------------------------------------------------------------------ |
| `blocks`          | gates            | X must close before Y is ready                                                             |
| `parent-child`    | gates            | epic/subtask; children blocked while parent is blocked                                     |
| `related`         | none             | soft cross-reference                                                                       |
| `discovered-from` | none             | created while working on the parent — **first-class provenance for agent-generated tasks** |

Status vocabulary: `open, in_progress, blocked, deferred, closed, tombstone, pinned, hooked`; soft-delete via tombstone fields (`deleted_at`, `deleted_by`, `delete_reason`) for synced issues — invalidate-don't-delete, same instinct as our bi-temporal facts. Distributed ID allocation uses content-hash-derived short IDs (4→6 chars, progressively lengthened) instead of sequential IDs, so two clones cannot both mint `bd-10`; merge = same id+hash → skip, same id+different hash → newer wins, else create. Unnecessary while llame is a single centralized instance, but the correct shape if offline/multi-instance sync ever lands.

**Ready-work is a deterministic SQL query, not app-level graph traversal** (`internal/storage/issueops/ready_work.go:93-140`): a built `WHERE` clause excluding issues blocked by open gating dependencies, with precomputed ID sets for deferred-parent children and — notably — **transitive** parent descendants. The comment preserves the bug story (GH#3396): parent filtering was originally a one-hop subquery, silently dropping grandchildren while the docs promised "descendants (recursive)". Lesson for llame's todos: if the API says subtree, the predicate needs a recursive CTE from day one; one-hop is a latent lie. Advertised at ~10ms offline, which validates computing readiness in Postgres directly with no dependency-resolution service.

## 2. Lease / heartbeat / reclaim (agent run ownership)

`internal/storage/issueops/lease.go` — the pattern our pg-boss durable runs can borrow wholesale:

- `ClaimReadyIssue` atomically claims (assignee + `lease_expires_at = now + TTL`); `DefaultLeaseTTL = 5min`, overridable per claim.
- Workers heartbeat well within the TTL; a dead worker stops heartbeating, the lease goes stale, and `bd reclaim` reverts the issue to ready. No coordinator process — liveness is inferred from the data.
- **The `row_lock` keystone.** Dolt has no row locking and merges concurrent commits _cell-by-cell_, so a heartbeat (writing `heartbeat_at`) and a close (writing `status`) on the same row would merge silently, letting a reclaim quietly revert an issue its owner had just closed. Fix: every status/ownership/lease-mutating path rewrites one shared `row_lock` cell to a fresh crypto-random value, forcing those writers to collide and trigger the serialization-conflict retry path. The file states the invariant: _any_ path mutating status/assignee/lease columns MUST rewrite `row_lock`; orthogonal-cell paths intentionally do not.

Postgres gives llame real row locks, so the `row_lock` trick itself is unnecessary, but the **explicitly documented co-mutation invariant** transfers: enumerate which column families race against reclaim/heartbeat, and make every mutator of that family serialize on the same conflict point. Our run-state transitions (`runs.status`, worker ownership, lease columns if we add them) deserve the same explicitness, e.g. a single `FOR UPDATE` target or version column named in a schema comment.

## 3. Wisp → digest compaction

`docs/ARCHITECTURE.md:294-334`, `docs/MOLECULES.md` — **molecules** are template workflows; spawning one creates **wisps**: ephemeral child issues tracking execution steps that live _only in the spawning agent's local DB_. They are never exported or synced ("they cannot resurrect from other clones — they were never there"), and `bd mol squash` hard-deletes them (no tombstones needed) after compressing the trace into **one permanent digest issue**. This is the cleanest shipped form of trace compaction: a cheap noisy execution trace, private to the executor, collapsed to a durable summary at completion, raw steps discarded by design. It rhymes with baro's run-decision-document lesson and maps onto llame's run event streams — the replayable event log is the wisp-equivalent (we keep ours for replay/audit) and a `run_digest`, produced at run completion and feeding `memory.consolidate` as an extraction source, is the squash. Never-synced data needs no tombstones, so deletion semantics are a function of replication scope; our per-user non-shared rows enjoy the same simplification and shared-scope rows do not. Complementing this, `bd prune` is **reference-aware**: closed issues still cited in open issues' text/comments are skipped by default — a good invariant for our `memory_citations` table, where a cited memory (or cited episodic range) is not eligible for hard-delete/prune while citations stand.

## 4. Anti-examples (memory chapter)

1. **`bd remember` + `bd prime`: the dump-everything injection.** The memory feature is a flat KV store (`kvPrefix + key → content`, key auto-slugified, update-in-place, substring search). `bd prime` — designed to run as a SessionStart hook — renders **all** memories into a `## Persistent Memories` markdown section: raw prose under key headers, **no** recalled-data framing, **no** provenance/citations, **no** confidence or lifecycle, and — because the store keeps **no timestamps** — entries ordered _alphabetically by key_. No recency, no relevance, no usage signal; the third dump-all specimen after baro, and the pattern our threshold-gated injection exists to avoid.
2. **No access control anywhere.** Identity is a free-text `actor`/`assignee` string plus a git-author string on Dolt commits; no authentication, no RBAC, no ACL — anyone who can reach the Dolt DB can read/write/delete everything. Coherent for single-repo dev tooling, the exact opposite of llame's tenancy model, and disqualifying as a multi-user reference.

## 5. Micro-patterns worth keeping despite §4

Two details inside the otherwise-anti-example `prime` renderer (`cmd/bd/prime.go:430-500`) are genuinely good. **The elision banner:** caps (`--max-memories`, `--max-memory-chars`) apply at whole-memory boundaries, at least one entry is always emitted, and when entries are elided a banner states _how many were dropped, which cap fired, and the exact command to browse the rest_ ("N more not shown; browse with `bd memories <keyword>`"), so a capped injection never silently pretends to be complete. Our eager-injection budget should do the same: when the token budget truncates recall, say so in the injected block and point at the `memory_search` tool. **Injection carries its own usage instructions** ("Stored via `bd remember`. Update in place with… Search with… Remove with…") — the tools demo riding along with the injected memory, which is precisely the one-shot-example pattern from our §7 addendum, independently arrived at.

## 6. Relevance to llame

Adopt into the todos/runs specs: the four-type dependency vocabulary with readiness semantics, especially `discovered-from` provenance, and the recursive-CTE-backed ready-work predicate (§1); lease+heartbeat+reclaim with a documented co-mutation invariant (§2); wisp→digest compaction and reference-aware pruning (§3); and the elision banner plus injection-carried tool instructions (§5). Reject the §4 anti-examples.
