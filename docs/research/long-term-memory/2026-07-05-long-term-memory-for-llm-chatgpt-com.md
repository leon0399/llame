# Long-Term Memory for LLM Assistants Across Chats

This report is written from the perspective of an LLM systems architect focused on persistent memory, retrieval, and agent infrastructure.

## Executive view

The strongest current conclusion is that **long-term memory for assistants is real, useful, and rapidly improving**, but the winning pattern is **not** “just give the model a giant context window” and it is **not** “one vector DB plus vibes.” The field is converging on a layered design: an immutable interaction log, selective episodic storage, compact semantic/profile memory, separate procedural memory, and a user- or project-visible knowledge substrate that can be searched and audited. On recent benchmarks, these layered systems consistently beat naïve full-context and flat-RAG baselines on long-horizon recall, temporal reasoning, and multi-session continuity, while using far fewer tokens. citeturn18academia0turn9academia3turn1academia0turn18academia1turn13academia2

For your use case, the most durable framework is **data-first memory, not prompt-first memory**: treat chats, notes, project docs, artifacts, and user-visible vault content as first-class records with provenance and access scope, then build retrieval, summarisation, and memory consolidation on top. That direction matches your own product documents unusually well: they already emphasise durable state over prompt tricks, a wiki-centric knowledge substrate, scope-aware ownership, and distinct user/project/group memory surfaces rather than one undifferentiated “memory blob.” fileciteturn0file0 fileciteturn0file1

If I reduce the current research landscape to one practical recommendation, it is this: **build the memory substrate as a governed data system with layered retrieval and provenance now; add decay, learned weighting, and more advanced forgetting policies later**. The recent papers most worth taking seriously are the ones that improve retrieval quality, evidence maintenance, update handling, and safety, not the ones that merely rename standard RAG with a flashy metaphor. citeturn6academia1turn12academia1turn5academia0turn5academia3turn10academia2

## Where the field has genuinely moved

The big shift in 2025–2026 is that memory research stopped treating the problem as plain “long context” and started treating it as **memory system design**. Foundational work such as _Generative Agents_, _MemoryBank_, and _MemGPT_ established the basic idea of storing experiences, reflecting over them, and retrieving them dynamically rather than replaying the entire past. More recent work sharpened that into explicit architectural choices: knowledge-graph memory in Zep/Graphiti, dynamic note-linking in A-MEM, structured fact extraction in Mem0 and Memori, temporal hierarchies in TiMem, and topic-document consolidation in Infini Memory. citeturn2academia0turn17academia1turn17academia0turn12academia1turn5academia0turn6academia1turn1academia0turn18academia1turn13academia2

The evaluation landscape has also become much better. _LoCoMo_ made the community care about very long conversations across many sessions rather than single-thread QA. _LongMemEval_ added tests for extraction, multi-session reasoning, temporal reasoning, knowledge updates, and abstention. Newer benchmarks then widened the aperture further: _MemoryAgentBench_ evaluates retrieval, learning, long-range understanding, and selective forgetting; _Mem2ActBench_ tests whether memory actually improves tool use and parameter grounding; _LoCoMo-Plus_ looks at latent “cognitive memory” rather than only explicit factual recall; _Memora_ adds forgetting-aware scoring for stale or superseded memory; _PersistBench_ focuses on safety failures caused by persistent memory; and _LongMemEval-V2_ evaluates whether agents can accumulate reusable experience in specialised web environments. In other words, the field has moved from “can you remember a fact?” to “can you remember the right thing, update it, ignore stale facts, avoid leakage, and use it to act correctly?” citeturn9academia3turn18academia0turn16academia0turn10academia0turn1academia3turn10academia2turn15academia2turn18academia3

A third real change is that consumer assistants have started shipping persistent memory as a mainstream product feature, not just a research idea. OpenAI expanded ChatGPT’s memory from explicit saved items toward referencing past chats; Google added past-chat recall to Gemini; and Microsoft introduced memory into Copilot as part of its broader push toward more personalised assistants. That proves demand is not hypothetical. At the same time, outside analysis has shown that memory creation is often opaque and heavily system-driven rather than purely user-declared, which matters a lot for trust, auditability, and enterprise or multi-user deployment. citeturn19news2turn19news1turn12news4turn8academia6

## MemPalace and the signal-to-hype ratio

Your instinct about MemPalace is basically right: **there is signal there, but not magic**. The most detailed critical analysis published so far argues that MemPalace’s headline gains come mainly from a **verbatim-first storage strategy**, a **deterministic zero-LLM write path**, and ordinary metadata-constrained vector retrieval, rather than from the “memory palace” spatial metaphor itself. In that reading, the “Wings → Rooms → Closets → Drawers” structure is useful mostly as a human-friendly organisational wrapper around standard filtering. The same analysis still credits MemPalace with real contributions: low wake-up token cost, offline-friendly ingestion, and a serious challenge to overly extractive memory pipelines that lose ground truth too early. citeturn20academia0

That is an important distinction. If you copy MemPalace, the parts most worth copying are **not** the branding metaphor. The valuable parts are: preserve raw evidence; keep a cheap write path; avoid forcing an LLM call on every write; separate the raw archive from query-time read bundles; and make retrieval auditable. Those ideas line up with other strong systems even when they use different representations. MemMachine stresses ground-truth-preserving episodic storage with contextual expansion around retrieved nuclei; Memori compresses conversation into summaries and semantic triples to lower token cost; TiMem uses temporal hierarchies; HiGMem uses event summaries as anchors so the answerer reads fewer but better turns; and Infini Memory moves toward maintainable topic documents rather than disconnected fragments. The convergence is striking: the field is not converging on one exact data structure, but it _is_ converging on “preserve evidence, consolidate selectively, retrieve iteratively, and do not trust flat similarity alone.” citeturn6academia2turn1academia0turn18academia1turn3academia3turn13academia2

So the clean verdict on MemPalace is this: **it is not mere buzz, but its strongest claims should be discounted unless independently replicated under matched models, prompts, and answer pipelines**. Cross-paper leaderboard comparisons in this area are notoriously fragile because different systems use different backbones, chunk granularities, query expansion tricks, and answer models. Treat MemPalace as an interesting design point, not as proof that spatial metaphors are the breakthrough. citeturn20academia0turn18academia0turn20academia1turn6academia2

## A framework that fits your product direction

The architecture that best fits your “brain / data-first / Obsidian vault style” direction is a **six-layer memory stack** with strict scoping and provenance. This aligns closely with your own spec and vision, which already frame the wiki as memory, insist on durable state, and distinguish user-, project-, and group-scoped resources. fileciteturn0file0 fileciteturn0file1

The first layer should be an **immutable event log**: every message, retrieval hit, tool result, edit, explicit memory save, and artifact reference is stored append-only. That is your system of record. Newer memory systems repeatedly rediscover that raw traces are necessary for auditability, re-indexing, debugging, and correcting consolidation mistakes. When a memory summary or profile fact is wrong, you need to be able to trace it back to the evidence, not just shrug at a vector embedding. citeturn6academia2turn13academia2turn17academia0

The second layer should be **short-term working memory** for the current run or chat band: rolling summary, active goal, temporary facts, open tool state, current plan. This is what the answerer sees first. The third layer should be **episodic memory**: preserved dialogue spans, full observations, and user-confirmed events, retrievable with surrounding context. The fourth should be **semantic/profile memory**: compact facts about preferences, habits, relationships, constraints, recurring tasks, and stable project facts. The fifth should be a **knowledge vault**: Obsidian-style notes, Markdown docs, project specs, wikis, artifacts, and curated documents that remain visible and editable as ordinary data rather than hidden assistant state. The sixth should be **procedural memory**: reusable prompts, slash commands, workflows, playbooks, and “how we do this here” knowledge. Research systems vary in naming, but this layered split maps well to MemGPT’s tiering, MIRIX’s multiple memory classes, MemOS’s memory-as-resource view, and the best recent conversational memory architectures. citeturn17academia0turn1academia2turn11academia1turn18academia1turn13academia2

For your multi-user and multi-assistant requirement, the crucial design choice is to model **memory scopes as first-class**, not as tags bolted onto a flat store. The clean split is: public/common memory, organisation or household shared memory, project memory, assistant/persona memory, user-private memory, and ephemeral session memory. Retrieval should always start with **policy and scope filtering before similarity ranking**. That is not just an enterprise nicety; it is a direct defence against inappropriate cross-domain recall and “why the hell did it bring up my private preference in this unrelated shared conversation?” failures documented by recent safety benchmarks. This also fits your spec’s group/project/user hierarchy and the idea of separate private vaults plus common shared memory surfaces. citeturn15academia2turn5academia3turn10academia2turn0file0turn0file1

For an Obsidian-compatible, data-first model, I would make the **vault the user-facing truth surface** and the memory index a derived system. In practice that means the assistant may write to hidden ephemeral memory or a semantic store for performance, but durable user-important facts should either be linkable to the vault or easily promotable there. This avoids the trap where the assistant “knows” things that users cannot inspect, correct, or merge into their actual knowledge base. Research is moving in the same direction: Infini Memory’s topic documents, A-MEM’s Zettelkasten-style links, and Zep’s temporal knowledge graph all push memory toward maintainable, inspectable structures rather than anonymous vectors alone. citeturn13academia2turn5academia0turn12academia1

## Governance, safety, and future-proofing for decay

The biggest reason not to treat memory as a simple retrieval add-on is that **persistent memory is a control surface and an attack surface**. PersistBench found high failure rates for cross-domain leakage and memory-induced sycophancy across many frontier and open models. The MemGate work argues that memory search itself is a trust boundary, because semantic similarity alone often retrieves memories that are related in embedding space but inappropriate in task context. Hidden in Memory then shows a more severe failure mode: persistent storage can be poisoned so that fabricated user facts are later retrieved and can drive downstream actions. citeturn15academia2turn5academia3turn4academia1

That means the write path should be conservative. Do **not** auto-save everything that looks salient. Separate explicit user instructions such as “remember this,” high-confidence factual extraction, inferred profile traits, sensitive traits, and third-party information. Keep provenance on every memory item: source message, source document, timestamp, scope, extraction confidence, whether the memory is user-declared or model-inferred, and what later evidence reaffirmed or contradicted it. Consumer-memory analysis shows this matters: a study of real ChatGPT memory entries found that the majority were created unilaterally by the system, with a substantial amount involving personal or psychological information. That is acceptable for a consumer product only if users can inspect, edit, and delete it; for your architecture, it argues strongly for visible and reviewable memory management. citeturn8academia6turn0file0turn0file1

This is also where your future “memory decay” idea becomes relevant, even if you do not implement it yet. The mistake would be to hard-code decay as a single universal score too early. A better framework is to make the schema decay-ready by storing the signals that future policies can use: event time, last-confirmed time, source trust, extraction confidence, explicit user pinning, contradiction edges, supersession edges, read frequency, scope, and retention class. Then later you can experiment with retrieval-time weighting, consolidation-time promotion/demotion, or policy-learned forgetting without redesigning the substrate. Recent work on forgetting-aware evaluation and maintainable memory strongly supports this “keep enough structure now, optimise the forgetting policy later” approach. citeturn10academia2turn13academia2turn16academia0

One further recommendation is to distinguish **forgetting** from **deletion**. For a serious assistant, the raw event log should usually remain immutable under retention policy, while higher-level semantic memory is what decays, gets superseded, or stops surfacing. That preserves auditability and lets you re-index later with a better policy. In other words, “memory decay” should mostly mean “reduced eligibility for retrieval or promotion,” not “erase history from the only source of truth.” That is especially important in shared environments, where private vaults, shared memory, and assistant operations need a clear forensic trail. citeturn13academia2turn17academia0turn0file0

## Papers and systems worth reading first

If I were building your framework now, I would prioritise the literature in this order.

- **Foundations:** _Generative Agents_, _MemoryBank_, and _MemGPT_ are still the best starting point for the core mental model: observation, reflection, retrieval, and memory tiers. They are older, but they explain why stateless chat breaks and why memory needs its own architecture. citeturn2academia0turn17academia1turn17academia0

- **Practical memory architectures:** _Mem0_, _A-MEM_, _Zep_, _TiMem_, _HiGMem_, _Memori_, _MemMachine_, and _Infini Memory_ are the most useful “how should I actually structure the system?” reading set. Together they cover extraction-centric, graph-centric, temporal-hierarchical, event-anchor, compact-structured, ground-truth-preserving, and topic-document approaches. citeturn6academia1turn5academia0turn12academia1turn18academia1turn3academia3turn1academia0turn6academia2turn13academia2

- **Benchmarks you should design against:** _LoCoMo_, _LongMemEval_, _MemoryAgentBench_, _Mem2ActBench_, _LoCoMo-Plus_, _Memora_, and _LongMemEval-V2_ together give a much better target than any single benchmark. They cover long conversations, action grounding, selective forgetting, latent constraints, knowledge updates, and environment experience. citeturn9academia3turn18academia0turn16academia0turn10academia0turn1academia3turn10academia2turn18academia3

- **Safety and trustworthiness:** _PersistBench_, _MemGate_, _Hidden in Memory_, and _The Algorithmic Self-Portrait_ are essential if you want a system that users can actually trust. They collectively show that relevance is not the same thing as appropriateness, and that stateful memory can create new failure modes that stateless assistants never had. citeturn15academia2turn5academia3turn4academia1turn8academia6

- **MemPalace specifically:** read the critical analysis before you let the branding influence your architecture. The paper’s central takeaway is very useful: preserve evidence and keep the write path cheap, but do not confuse a good storage discipline with proof that the spatial metaphor is the secret sauce. citeturn20academia0

- **If you later want multimodal or workplace-agent memory:** _MIRIX_, _TeleMem_, and _LongMemEval-V2_ are the current signals that memory is widening beyond text chat into screenshots, richer behavioural traces, and specialised environment experience. That is promising, but I would treat it as a phase-two concern unless your assistant will actively observe screens or operate web environments. citeturn1academia2turn6academia3turn18academia3

## Bottom line for your framework

The architecture I would back for your project is **not** a pure MemPalace clone and **not** a pure hidden-memory SaaS assistant model. It is a **layered, scoped, provenance-heavy memory substrate** in which a visible wiki or vault acts as the enduring knowledge surface; append-only interaction logs preserve ground truth; semantic/profile memory is compact and inspectable; retrieval is hybrid and policy-gated; and shared memory is represented as shared scopes, not as a fused cross-user blob. That conclusion is supported both by the recent research arc and by the direction in your own spec and vision documents. citeturn20academia0turn6academia2turn13academia2turn5academia3turn15academia2turn0file0turn0file1

If you want the shortest possible strategic answer: **build the framework around evidence preservation, memory scopes, user-visible vault integration, and trustworthy retrieval now; leave decay as a later policy layer over richly structured memory records**. That gives you the best path to Obsidian-style knowledge, multi-user shared/common memory, private vaults, future decay, and assistant continuity that feels intelligent rather than creepy or brittle. citeturn10academia2turn13academia2turn5academia3turn0file0turn0file1
