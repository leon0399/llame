Implementation is a single `gh stack` rooted on `master`, one PR per layer, bottom to top. The
bottom layer is this change itself — proposal, specs, design, and this task list — so the design is
reviewed and merged before any code builds on it. Every layer is published with
`gh stack submit --auto`, implemented with `$openspec-apply-change`, and monitored per
`CONTRIBUTING.md`; the finalize layer closes #338.

```text
(master) <- tool-search/proposal
         <- tool-search/budget
         <- tool-search/loop
         <- tool-search/openai-native
         <- tool-search/finalize
```

Every layer leaves the repository shippable: after `budget` merges, the threshold, tier
computation, schema fields, and reserved id exist but nothing is persisted, bound, or shown, and
every tool is still declared, so snapshots, receipts, and provider requests stay byte-identical to
`master`; after `loop` merges, deferral engages only for catalogs beyond the budget under
the default `harness` strategy; after `openai-native` merges, operators may opt `gpt-5.4`-and-later
models into the provider's own search. Each layer's final task is its exit criterion.

## 2. `tool-search/loop` — `tool_search`, per-step declaration, promotion (design D1, D5, D6, D7, D9)

- [ ] 2.2 Implement the `tool_search` executor over the Run's bound declarations: exact `select` resolution, case-insensitive token match over id (`_`/`-` split) and neutralized description with the D7 ranking and stable tie-break, result `{ status: 'success', tools: [...], notFound: [...], notLoaded: [...] }` sized by the executor so whole declarations that would exceed the result cap are dropped into `notLoaded` and the recorded result is never truncated; verify by unit tests for exact select, a query that matches ids only, a query that matches descriptions only, a `limit` above 20 and a `select` above 20 entries refused as `invalid_input` by schema validation before the executor runs, an unbound id reported under `notFound`, and an oversized declaration reported under `notLoaded` with the result below the cap

- [ ] 2.5 Add cross-Run promotion at accept: candidates are `previousRun.loaded_tool_ids` (most recent first) then `previousSnapshot`'s promoted MCP ids (only when that snapshot had discoverable tools or a `declaration_budget_exceeded` cut), skipped when the turn starts a new disclosure epoch; verify by integration test that the next Run declares a previously loaded tool on step one and records it outside `discoverable_tool_ids`, that a previous within-budget Run promotes nothing, that promotion stops at the budget with the most recent loads first, that a promotion which cuts the entire remaining inventory still carries into the following Run, and that a Run after a new compaction checkpoint reverts to the default partition while a search result kept in the compaction tail grants no callability

## 3. `tool-search/openai-native` — the `openai` strategy (design D1, D11)

Owns only the second transport. Reviewed alone because it is the only layer that changes a
Responses request shape. Task 3.0 is a spike whose exit criterion gates the rest of the layer.

- [ ] 3.0 **Spike:** against the real Responses API on a `gpt-5.4`-or-later model, send a second-Run request that replays a prior `tool_search` call with llame's text tool result and natively redeclares the promoted tool; record which of the two candidate replay shapes in design D11 the API accepts (text function output, or persisted structured output emitted as `tool_search_output`) and whether a tool may be both natively declared and present in a replayed `tool_search_output`; write the outcome into design D11 and pick the persisted shape for `tool_search` observations before 3.3
- [ ] 3.1 Add optional `models[].toolSearch` (`harness` | `openai`, default `harness`) to `llame-config.ts`, the loader, and the JSON Schema, boot-failing `openai` on any provider other than the native OpenAI one and on unknown values; verify by unit tests per the `instance-config` delta that failures name the model id and the key
- [ ] 3.2 Thread the strategy into the snapshot (`tool_search_strategy`), the receipt label, and `ModelStreamInput`; verify by unit test that a `harness` model's snapshot and hashes are byte-identical to layer 2's
- [ ] 3.3 In `openai-model-client.ts`, when the strategy is `openai`: send discoverable declarations with `providerOptions.openai.deferLoading: true` and promoted declarations without it, bind `openai.tools.toolSearch({ execution: 'client', description, parameters })` with the `select`/`query`/`limit` shape without the enum, and add the adapter that unwraps the SDK's `{ arguments, call_id }` input into the shared executor and maps each delivered declaration to `{ type: 'function', name, description, parameters, defer_loading: true }` in the returned `tools`; leave `prepareStep` to the cap only and keep the 2.3 execute-wrapper gate; verify by unit test against the raw request body that `defer_loading: true` is on exactly the discoverable ids, promoted ids carry no marker, the `tool_search` tool has `execution: "client"`, and the search result is emitted as a `tool_search_output` item echoing `call_id` whose `tools` equal the recorded loaded ids
