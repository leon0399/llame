## Why

Chat retrieval is lexical only. The recorded baseline (`apps/api/src/search/chat/eval/BASELINE.md`) measures Recall@10 = 1.00 on exact-title, exact-content, code, and typo queries — and **0.00 with a 1.00 zero-result rate on paraphrase**, because a query that shares no tokens with the chat cannot be reached by FTS or trigram at all. The same baseline records that its Russian/Spanish rows score 1.00 only because the fixture queries reuse surface word forms, and that `simple` FTS performs no stemming, so inflected Russian will regress on real multilingual data.

Closing that gap needs a vector leg, and a vector leg needs storage, a provider boundary, and a backfilled corpus before any query can use it. This change lands that substrate **without touching the query path**, so the async and provider machinery bakes in production while search behavior stays exactly as it is today. Flipping retrieval on is a separate, separately reviewable change.

## What Changes

- **BREAKING (deployment):** Postgres must provide the `vector` extension. `compose.yaml`, the integration-test Testcontainers image, the Playwright E2E database image, and CI move off `postgres:17-alpine` to a digest-pinned pgvector image; pgvector joins `pg_trgm` as a documented self-host requirement in README and AGENTS. `pg_trgm` shipped in the base image and needed no swap; `vector` does not.
- An **embedding-model catalog** keyed by a stable internal key, carrying provider connection, provider-side model, revision, dimensions, distance metric, and optional asymmetric document/query prefixes. Application code and stored vectors reference internal keys only; provider-side identifiers never leak past the adapter. **Which model serves a corpus is per-corpus**, not one global flip, so corpora that backfill at different speeds cannot strand each other. The catalog is operator config-as-code, with a small database ledger recording each key's binding so a silent redefinition of an in-use key is rejected rather than reinterpreting existing vectors. (Design decision D1 — this replaces the database-table registry sketched on #196.)
- **Embeddings as nullable columns on the existing projection table** — vector, model key, embedded content hash, input version, and failure reason — so a document is at most one vector and tenant isolation is inherited rather than restated. One model serves a corpus at a time; a model change re-embeds in place. (Design decision D2 — this replaces the separate embedding table sketched on #196, whose only justification was a parallel two-model migration nobody asked for.)
- A **content-hash validity rule**: an embedding is valid only while its recorded content hash and input version still match the document. Results arriving after the content was edited or deleted are dropped, never applied, so a late provider response can never restore deleted content — and a rebuild clears the embedding in the same statement that rewrites content.
- **Terminal failures recorded in place** so a permanently unembeddable document is neither retried forever nor silently hidden, superseded automatically when content, input version, or model changes, and clearable by an operator command.
- **No completeness gate.** Retrieval fuses whatever legs exist — a partially embedded corpus is fully searchable, with the vector leg contributing where vectors are present. A per-row model-key filter keeps two embedding spaces from ever meeting in one ranking.
- A **provider-neutral embedding backend** behind one interface, with an OpenAI-compatible adapter that covers both self-hosted (Ollama) and cloud endpoints.
- An **asynchronous embedding pipeline** on its own coalesced queue, enqueued post-commit by every path that changes a chat's projection — the inline turn-completion rebuild, the reindex worker, and fork — plus a cross-tenant sweep that discovers _embedding_ lag, which the existing lexical staleness predicate cannot see. A dedicated worker embeds, validates, and persists. Lexical freshness is unaffected; embedding freshness is allowed to lag.
- A **chunker version bump** (#517) so a single message larger than the chunk budget is split into budget-sized parts, each continuation part carrying a bounded excerpt of the question it answers. Today such a message is emitted as one oversized document — harmless lexically, unembeddable in practice. A message that fits chunks exactly as before, so the recorded eval baseline does not move.
- **Explicit bulk work, automatic incremental work**: ordinary turns embed automatically, while a newly declared model or an input-version bump is advanced only by an operator-invoked `backfill`. A configuration edit never initiates corpus-scale provider spend. A `prune` command removes vectors of a model no longer declared; nothing is ever auto-deleted.
- **Off by default, and configured only in `llame.config.json`**: embeddings are inert until an operator declares `embeddingModels[]` and a per-corpus intended model in the config file. There is no environment-variable switch, no database setting, and no per-user or per-tenant control. With no such configuration the instance runs clean and search stays lexical; absent configuration is never an error path.
- **A fourth worker group, `search-embed`**, so embedding concurrency — which is the provider spend and saturation dial — is an operator setting rather than a source constant, and so network-bound embedding does not share a concurrency number or a retry policy with DB-bound lexical rebuilds.
- **No query-path change.** `ChatsRepository.searchByOwner`, its ranking, snippets, and output contract are untouched, and the eval baseline is expected to be byte-identical after this change.

## Capabilities

### New Capabilities

- `search-embeddings`: the derived vector layer over the search projection — model registry and per-corpus active-model selection, per-corpus vector storage and its tenant-isolation invariants, the content-hash validity rule, the provider-neutral backend boundary, asynchronous embedding production and backfill, fail-closed degrade when unconfigured, and model-migration discipline. Like the lexical projection, it is derived state that is fully rebuildable from canonical `chats`/`messages`.

### Modified Capabilities

- `search-projection`: two requirements change. Its **chunking** requirement currently mandates splitting on message boundaries, which emits a single oversized message as one oversized document — the projection defect that makes such a document unembeddable; it gains intra-message splitting with a bounded anchor on continuation parts, under a chunker version bump. Its **platform-dependency** requirement states "pgvector is explicitly NOT part of this capability (phase 2)" and pins clean provisioning to a stock `postgres:17-alpine`; both become false. Indexing, discovery, isolation, and deletion are unchanged — the async-coalescing requirement already names "phase-2 embedding work", and because vectors live in their own table rather than a column on the projection, the tier writer partition needs no new invariant.
- `instance-config`: an optional embedding-model catalog is added to `llame.config.json`, referencing the existing `providers[].id` list rather than introducing a parallel credential concept, under the existing schema-as-boot-validator and `{env:...}` / `{path:...}` rules. Embedding selection is operator config because background indexing is instance-scoped rather than per-request; absent configuration degrades to lexical rather than failing boot.

`chat-search` is deliberately **not** modified. Its matching semantics, fused ranking, output contract, and eval baseline are the subject of the follow-on hybrid-retrieval change.

## Impact

- **Deployment:** `compose.yaml`, `apps/api/vitest.integration.global-setup.mts`, `playwright.config.ts` (`E2E_DB_PG_IMAGE`), CI Postgres services, README and AGENTS self-host requirements. Existing self-hosters must move to a pgvector-capable image before upgrading.
- **Schema:** one migration adding the `vector` extension, five nullable embedding columns on `search_chat_documents`, a model-binding ledger (instance-global operator state, no tenant column, so no RLS), and a BYPASSRLS-owned coverage-discovery function alongside the existing lexical one. Isolation is inherited from the projection's existing FORCE-RLS policy; cross-tenant negatives are extended to cover the embedding columns explicitly.
- **Code:** `apps/api/src/search/core/` gains the corpus-agnostic backend interface and one OpenAI-compatible adapter; an embed worker and queue join the existing reindex worker in `apps/api/src/search/`. `SearchModule` stays a leaf — it imports no new module. `WORKER_GROUPS` gains `search-embed`, with matching config-schema, profile, and `docs/scaling.md` updates.
- **Operations:** a new queue, worker, and worker group to observe; three operator commands (`backfill`, `prune`, `retry-failed`); per-chat coverage reported as distinct embedded/failed/outstanding counts; and one new outbound provider dependency when configured.
- **Cost:** embedding an existing corpus is a one-time provider spend proportional to chunk count, and ongoing spend proportional to new turns. A self-hosted backend makes both zero.
- **Rebuild:** the chunker version bump re-chunks every existing chat through the discovery sweep — the mechanism that already exists for a version change. Verified not to alter the eval baseline, whose fixtures top out at 184 characters.
- **Not affected:** the command palette, `search_conversations`, ranking, snippets, and every existing search test — this change is intended to be invisible to users until the follow-on retrieval change lands.
