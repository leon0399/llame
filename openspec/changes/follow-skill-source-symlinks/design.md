## Context

See proposal.md for motivation. The state that shapes the approach:

- `apps/api/src/skills/skill-catalog.ts` `resolvePackageDirectory` (307-341): a non-link child is a package if it is a directory; a link is resolved through the `realPath` port, refused when the real path is outside every configured root, then checked to be a directory through `fileKind`, whose link branch reports a link-to-directory as `unavailable` (70-84) and so only works because it receives an already-canonical path. `escapesPackage` (414-427) contains `SKILL.md` and sidecar links to the package's real directory. `apps/api/src/skills/skill-target.ts` `containIntoPackage` (167-184) contains `skill://<name>/<path>` reads, using `nearestExistingAncestor` (188-202) and `isInside` (204-206). `isInside` is duplicated verbatim in both files. Configured source roots are `realpath`-resolved so containment compares real paths on both sides.
- `packages/native-file-tools/src/read.ts` exposes two readers. `readFile({path})` follows links but accepts no `displayPath`, selector, or reserve and re-derives the target from the literal path. `readResolvedFile(hostPath, options)` takes those options, hard-codes `followSymlinks: false`, and refuses a link at the leaf via `lstat` (`resolveResolvedTarget`, 122-132); its docstring says "there is no caller for whom that is correct". It is what `kb://` and `skill://` use today (`native-files.ts:150,223`). A `skill://` read therefore needs a follow option on `readResolvedFile`, not a call-site switch.
- The read result is one flat object (`ReadSuccessBase`, `source-lines.ts:13-26`) built in `emptyReadResult` and `emptyMultiReadResult`, measured whole against the result cap on every appended line (`source-lines.ts:113`), and serialized whole as the tool result the model sees. A field added after streaming would not be counted.
- The skill result is `{ ...result, ...envelope }` (`native-files.ts:156`); the envelope's five fixed keys are reserved before content (`native-files.ts:145-147`, `skill-results.ts:36-46`). A field outside the envelope is not reserved, and a skill field named `realPath` would overwrite a reader field of the same name.
- `packages/native-file-tools/src/directory-listing.ts` classifies an entry from the dirent alone (`classifyEntry`, 67-74) through a `DirectoryPort` that exposes only `opendir` (15-21); `DirEntry` is `{ name, kind }`; `compareEntries` promotes only `kind === 'directory'` (87-92); `readChildDirs` descends only `kind === 'directory'` (148-150). Three tests supply fake ports. The same renderer serves host paths, `kb://`, and `skill://`.
- `kb://` results "SHALL expose no configured root, resolved child path, hosted owner ID, credential, worker identity, or raw filesystem diagnostic" (`native-file-tools/spec.md:660-663`), and `kb://` reads refuse every link component (`knowledge-filesystem-host-path.ts`). Nothing filters link entries out of a `kb://` listing.
- Discovery is one level deep, so no traversal cycle can arise; a self-referential link fails `stat` with `ELOOP` and becomes an unavailable entry.
- Reference behavior (revisions in #868): oh-my-pi admits symlinked children and publishes `path.join(dir, entry.name, 'SKILL.md')` with no `realpath` (`discovery/helpers.ts:495-502`); Codex follows for user, repo, and admin roots; OpenCode always follows; Claude Code documents cross-disk skill links. None contains resources inside a personal-root package. No harness exposes link descent in a model-facing listing; OMP renders a link as an unmarked plain entry, OpenCode as `name/` after a `stat`.

## Goals / Non-Goals

**Goals:**

- Skills follow operating-system link semantics with no resolution, verification, or containment code.
- Published paths are what discovery walked, so the model and the owner see the same path the operator configured; the real location is advertised beside them.
- A model without shell access learns where a link leads from a listing.

**Non-Goals:**

- Per-source link configuration; Agent Plugins (#784) may introduce a contained source class later.
- Deduplication of two differently named entries that resolve to one directory; override-by-name covers the shared-name case.
- Any change to `kb://` link refusal or `kb://` path privacy, `bash` cwd resolution, or descending links inside a listing (#714, closed).
- Cycle detection; discovery does not recurse and listings do not descend links.
- `tree`-style box-drawing glyphs in listings.

## Decisions

**D1 Trust is a property of the source; no link verification.** A configured source is trusted by being configured, so every link reachable from it is the operator's choice. Alternative A: keep root-union containment and document listing real roots as sources. Rejected: every reference harness follows for operator roots. Alternative B: follow package links but keep package-internal containment. Rejected: it keeps all three containment algorithms and the `realpath` port for a boundary no reference harness enforces on a personal root, and the operator who can place a package link can place an internal one. The one instance shape where this widens reach, `skill://` allowlisted without host `read`, is accepted because only the operator can place the links.

**D2 No `realpath` for resolution or containment in skills.** Discovery classifies a child by following `stat` and the `SKILL.md` presence check, so `fileKind` reports the followed target's kind for a link (`directory` through a link-to-directory) while keeping its `lstat` branch for dangling detection. Reads open the discovered path with `readResolvedFile` under a new opt-in `followSymlinks` option that `kb://` never sets; the option is threaded through target resolution, the file stream, and the miss path so a miss under a linked parent still yields sibling suggestions, and under it a followed target that is neither a regular file nor a directory is refused before any open, so a link to a FIFO or device is never opened. Published `skillDirectory` and `resolvedPath` are the discovered link paths, as oh-my-pi publishes them and as this harness's own sessions show (`[Skill directory: ~/.agents/skills/<name>]`); scripts resolve through the link at exec time. The real directory is advertised as `realSkillDirectory` in the envelope when it differs (D7), so a model without shell access can still learn where the package lives; if that `realpath` fails the field is omitted and the read proceeds. That is the only `realpath` in the skills path and it is display only. Alternative: publish real paths as `skillDirectory`. Rejected: the operator configured the link path, and every reference harness publishes it.

**D3 Dangling and non-directory links stay visible.** A child link whose target is missing remains an unavailable entry naming the unresolved link; a child link resolving to a regular file becomes an unavailable entry naming the target kind, where today it is silently not a package. Both are inspectable through `GET /api/v1/skills`. Alternative: skip silently as Codex's plugin mode does. Rejected: the operator placed the link and should see why it is not a skill.

**D4 `agent-skills` owns the rule.** The read tool's skill-locator requirement keeps only what a read does (envelope, selectors, special-file refusal) and defers link semantics to discovery. The "Escaping link fails" scenario survives with a special-file body because OpenSpec refuses a MODIFIED block that drops a scenario; the finalize layer renames it in the canonical file after sync.

**D5 Deletion, not replacement.** No containment helper is introduced; nothing remains to consolidate, and the Knowledge Space check stays the single implementation of its own rule.

**D6 Listings say where a link leads, except on `kb://`.** `- name@/ -> /real/target` (directory target), `- name@ -> /real/target` (file target), `- name@? -> raw-link-text` (dangling or special). The target is canonical (`readlink -f`), because a model with no shell cannot chain a multi-hop link itself (a Nix home-manager link resolves store path then dotfiles). The `DirectoryPort` gains the metadata, `realpath`, and `readlink` operations the renderer needs, `DirEntry` gains the link's target kind and target beside its own kind, the descent filter and the comparator stay keyed on the entry's own kind so a link is never descended and sorts by name among non-directories, and link metadata is resolved in one bounded pass after classification, for the requested level and the capped head of each child directory. A `kb://` listing keeps the bare `- name@` through an explicit `linkTargets: false` listing option the Knowledge caller passes, threaded from `NativeReadOptions` through `ReadTarget` to `DirectoryListingOptions`, so the scheme-agnostic renderer never inspects a `kb://` prefix; it is a separate option from `followSymlinks`, which governs opening, not publication. Alternative A: raw link text as `ls -l` shows; rejected, leaves the second hop unknowable. Alternative B: opt-in descent with a visited set (#714 as written); rejected, no reference harness exposes descent to a model and the root-target rule already gives the model the same information on request. The bullet shape is kept: OMP renders the identical indented `- name/` form, box-drawing glyphs cost tokens on every line, and vertical rails make a line's bytes depend on its siblings.

**D7 Reads report the real path.** A host-path file read whose canonical path differs from the normalized path given carries `realPath` on `ReadSuccessBase`. The canonical path is resolved once in `resolveReadTarget`, on both of its host branches, and stored on `ReadTarget`; the two synchronous result constructors only copy it, before any line is measured, so it counts against the cap like every other field. `applySelectorSuffix` and `resolveResolvedTarget` never set it, which is what keeps it off `kb://` and `skill://`. Header and numbering are those of the path as given; a directory listing never carries it. `kb://` and `skill://` reads never carry it. The `skill://` envelope keeps link-path `skillDirectory` and `resolvedPath` (D2) and adds `realSkillDirectory`, resolved in `resolveSkillLocator` and included in `skillResultEnvelope` so the existing reserve covers it and no name collides with the reader field.

## Risks / Trade-offs

- [A source pointed at a third-party checkout could link to arbitrary host files] → Sources are operator-configured only; the same operator can allowlist host `read`. Documented in `docs/skills.md` and `docs/native-files.md`. A contained source class can arrive with #784 without reopening this decision.
- [Inverting refusal tests hides a regression in the dangling-link path] → The dangling `SKILL.md` and sidecar tests stay unmodified and are asserted separately; every inverted or retargeted test is named in tasks with its new assertion and a name that matches it.
- [Adding `followSymlinks` to the shared reader loosens `kb://`] → The option defaults to `false`, `kb://` never passes it, and the existing `kb://` link tests stay unmodified.
- [Folding a directory-target link into `kind: 'directory'` would descend it] → `DirEntry` keeps the entry's own kind separate from the target kind; the descent filter and comparator read only the former (D6), and a listing test asserts a linked directory is not descended.
- [`realPath` or `realSkillDirectory` added after measurement overruns the result cap] → Both are set before measurement (D7).
- [A `kb://` listing leaks a host path through the shared renderer] → Explicit `kb://` carve-out in the spec and a `kb://` listing test with a link entry.

## Migration Plan

Two implementation layers. Skills: extend `fileKind` to report a link's followed kind, add `followSymlinks` to `readResolvedFile`, delete the containment code and the `realPath` port, invert or retarget the named tests, update `docs/skills.md` and `docs/native-files.md`. Listing and details: extend `DirectoryPort` and `DirEntry`, render target kind and canonical target with the `kb://` carve-out, add `realPath` to host read results and `realSkillDirectory` to the skill envelope, update the listing tests and the read tool description. No data or configuration migration. An operator who added real roots as a workaround may remove them.
