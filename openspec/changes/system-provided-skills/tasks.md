## 1. Proposal layer: system-provided-skills/proposal

Exact delivery stack: `master <- system-provided-skills/proposal <- system-provided-skills/catalog <- system-provided-skills/read <- system-provided-skills/prompt <- system-provided-skills/activation <- system-provided-skills/notices <- system-provided-skills/finalize`.

The proposal layer owns only planning artifacts. The catalog layer owns `skills.directories` configuration, bounded discovery, package validation, invocation-control resolution, operator diagnostics, and the authenticated `GET /api/v1/skills` inspection surface, with no model-facing behavior. The read layer owns read-only `skill://` locators in native `read`, package containment, the path-publishing result envelope, read eligibility, and canonical permission projection; manual-only body reads refuse until the activation layer supplies the turn's selections. The prompt layer owns the `skills` Handlebars projection namespace, the packaged default catalog block, the frozen per-epoch baseline on the chat row, lazy re-baseline after compaction, and the bound with omitted-count disclosure. The activation layer owns `$skill` mention parsing, bounded pre-request loading through common admission, `skill-activation` context items, system-origin provenance, idempotent recovery, and `GET /api/v1/runs/:id/context-items`. The notices layer owns `skill-catalog` added/removed notices against the told state, the supersession snapshot on overflow, and told-state persistence; its PR closes #770. The finalize layer owns canonical documentation sync, task records, and archive movement only.

Use `$gh-stack` for every stack operation and `$openspec-apply-change` for every implementation layer; create only the next approved layer. Publication and merging require the permissions in CONTRIBUTING.md.
